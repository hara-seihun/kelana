# Fixed 45-token recent-V KIVI rate control

**Outcome.** An original KIVI 4-bit/G32 cache with unchanged shared K **R32**, and only a longer **45-token recent-V buffer**, reduces the original two-head inspected-held complete post-O pair relative squared error from **0.000155355 → 0.000136901** (11.88% less SSE) at **54,688 B peak live cache**, versus original KIVI **52,400 B**. No offline training, model-specific table, new source or GPU is involved. This is **not** KIVI's named default residual allocation and not a bitwidth/group/rank sweep. The previously frozen train-metric K-code assignment gets **0.000135159** at **54,704 B** (just 16 B more), so the extra 2,304 metric bytes buy only a further ~1.27% reduction in held pair O error over this simple retention arm on these windows, while also improving attention KL and paying substantially more K-flush work. Neither reader strictly dominates every quality/work coordinate; there is no native latency claim or full-model inference conclusion.

## Rule, original observer and byte chronology (frozen before scoring)

The [original KIVI 4/4 G32 R32 owner](../kivi-causal-cache/) supplies the original Qwen3-0.6B layer-0 two-query-head/shared-K/V group, immutable source/teacher, eight training and four inspected-held 256-token windows, actual original 32-key and per-token V paid flush events. K source is Qwen-normalized/RoPE with original BF16 recent rounding and KIVI per-channel K nibble/FP16 field bytes **unchanged**. V is original BF16-projected source; all V 4-bit/per-token/32-coordinate quantizers and actual FP16 fields are **unchanged**. The original recent V R32 retains 32 tokens after each query and flushes its oldest only when the **preflush** recent buffer reaches 33. This single control sets **R45**: at the query where preflush buffer reaches **46**, that query still sees all 46 BF16 V vectors, then its oldest V flushes and 45 remain. At its delayed flush the stored V80B event is byte-identical to the one original KIVI generated for **the same source token 13 queries earlier**; this is causal because the original event itself was generated from that token alone. No future token content enters any early query. Q/K source, two heads, Q/K norms, RoPE, entire original BF16 V and O weights, stable causal softmax, and the K packing schedule are unchanged. No model-specific descriptor or running calibration is added; the changed residual threshold is a fixed program constant.

Thus **13 extra recent tokens displace 13 packed tokens**: `13×(256−80)=2,288 B`, on preflush peak and final postflush. The extra2,288 B is 16 B less than the one model-group FP16 U/D image (+2,304 B) in [`../kivi-response-metric/`](../kivi-response-metric/) at the same original KIVI state. The common original static two-Q/K/V/O/gamma group state is **1,573,376 B**, and shared 2-B position counter is excluded from both shown cache states. The eight K/211 V stored flush events per window are chronology evidence, **not a second live cache**.

## Complete original-source acceptance

[`program.py`](program.py) inserts only the current source BF16 K/V and scores the current two-head query from the **actual preflush cache**, then performs unchanged K flush or delayed V flush. For every window, it records final paid image `PANEL-WINDOW-final.bin` (48,880 B), chronological event log `PANEL-WINDOW-flush.bin`, 256 `PANEL-WINDOW-prefixes.json` preflush state hashes and complete output/loss `PANEL-WINDOW.json`. All eight K events are the original bytes at the original time; all 211 V events are the original bytes for their source token at its new delayed time. [`replay.py`](replay.py) reads only each candidate event when causal time arrives, re-forms all 256 preflush hashes, checks K event identity, V event identity and each V FP16 field/nibble against the source token independently, verifies final image, and computes the original full two-head scores, softmax, V mixture and all **1,024 original O output columns**. It checks the per-head attention KL equals unchanged KIVI on every window. All **eight train and four held** windows pass. [`results.json`](results.json) aggregates absolute squared-error numerator/reference energy instead of averaging window ratios. No final-token cache is decoded retroactively for an early query.

Each of the four inspected-held pair outputs improves against original KIVI; no head score/attention KL improves because original K fields, recent K, Q and logits are **identical**. The fixed metric assignment's 1.27% pair advantage over R45 at +16 B is a different error channel: it improves K logits but incurs 2,304 B model-specific preparation plus an extra 128-coordinate rank8 sweep for each flushed key. R45 is **not** an improved trained key method and does not replace the metric image where score KL matters. The control establishes that the metric gain is comparable to ordinary recent-V retention at essentially the same total bytes, making rate-accounting essential before attributing novelty to the metric.

## Online work and scope

The16B comparison above is for one sequence. The V45 increment is2,288B **per sequence**, while the metric is2,304B of immutable **model-group** data shareable across sequences. Their represented peaks are54,688N versus52,400N+2,304B, respectively; the metric representation is smaller from N=2. This does not include the CPU's9,216B decoded FP64 metric arrays, other scratch or an unbuilt native prepared form. Encoding work still repeats per sequence; neither the single-sequence difference nor the concurrency crossover establishes latency.

At t256 preflush the R45 cache reads 210 rather than 223 quantized V token records and 46 rather than 33 BF16 V vectors. Per query/head, this substitutes 13×128 quantized V code/FP16 affine contributions with 13×128 direct BF16 weighted contributions; it reduces grouped field/nibble reads but increases BF16 cache bytes and traffic. K code loads, both 128D Q/K score reductions, two stable softmax rows and the **262,144 common full O multiply-add terms** are unchanged. No extra V quantizer computation is needed for each token eventually flushed; it is delayed by 13 positions, while at the finite 256-token endpoint 211 rather than 224 V flushes have occurred. Recent FIFO requires capacity for 13 more BF16 tokens and moves/retains them until their causal flush. There is no offline fitting or static metric, unlike the response-metric arm. Current CPU acceptance temporarily decodes the 256×128 K and V arrays (**up to 262,144 B scratch**) and does not establish a 54,688 B total CPU process. Neither arm has native execution timing here; do not infer throughput from less quantized V math.
