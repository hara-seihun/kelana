## Stage gate

After source/layout/receipts review, the parent can admit exactly one stage by writing **`<source_hash> accept held-0`** to `launch-approved.sha256`, then invoke `bash run-stage.sh accept held-0`. The script validates the full prelaunch receipt *before any GPU call*, consumes that approval once, refuses an existing attempt, acquires nonblocking `/tmp/kelana-gpu-measure.lock`, confirms a live nonzero `bonsai-halo.service` PID, and runs at most 45 seconds under `gpu-run --host-mib 1024 --gtt-mib 512`; the same resident PID/state must survive. A stage has a raw attempt receipt and exact-host all-phase audit. `stage_receipt.py` verifies full-output max absolute and relative L2 are each ≤0.005 against the appropriate independent CPU map, four endpoint results per window (two arms × two held positions), sixteen acceptance outputs across four windows. All four independent `accept held-N` stages must pass and remain hash-pinned before **any** `timing held-N` stage may run. Timing takes four fresh empty replays **per arm per window**, alternates first arm `(window+round)%2`, and gives 8 endpoints ×4 =32 matched pairs. Each stage requires its own approval (`<source_hash> timing held-N`). Raw lifecycle, event, host audit and arm output files are retained and hashed. A failed parity is a failure; changing the reader, precision or reduction creates a new source and requires renewed review, not an acceptance retune.

All approval markers were consumed. The attempt logs, raw rows, per-stage receipts, actual outputs and lossless states are the device evidence; compile resources alone are not a speed measurement. Completed attempts are immutable and the gate refuses their replacement. No further placement or coefficient variant is assigned.
