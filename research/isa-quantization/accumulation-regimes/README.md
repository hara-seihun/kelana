# Quantize for a single integer accumulator

Choosing one scale for an entire integer dot can remove a register-lifetime boundary. With a scale per K-block, a matrix tile has an int32 partial sum and an FP32 running output at the same time. With one weight scale per output row and one activation scale per input row, the entire dot can stay int32 until the final conversion. This is a different proposal from [compact scaled FP16](../../../ffn/batched/compact-scaled/README.md): the operand remains integer and there is no FP16 WMMA inner loop. The price is that the quantizer loses its blockwise scale freedom on **both** operands.

The small exact result is more cautionary than promotional. Within a ternary-code family, shared-scale quantization crosses the declared eight-tile register threshold and saves two of five model bytes on a four-weight example, at a known response error. A stronger *same-byte* four-level codebook represents the planted teacher exactly. Scale coherence alone is therefore not a format-independent reason to choose the ternary candidate.

## Exact response experiment

For a four-coordinate row, use two consecutive K-blocks of length two and all 81 inputs in `{-1,0,1}^4`. Outputs are rational dots, without floating accumulation error. The same input code and its unit scale serve both blocks. Weight codes are ternary, `{-1,0,1}`. Each step is stored as FP16; all selected steps are exactly representable. The model-byte count is one packed byte of four two-bit codes plus two bytes per step. Input, code expansion, instructions, output and preparation are not charged as model bytes; they must be charged when comparing programs.

For uniform independent ternary inputs, `MSE = (2/3) sum_i (w_i - q_i s_i)^2`. On the entire input box, `max |error| = sum_i |w_i - q_i s_i|`. These are *complete-domain* calculations, not sample estimates. The first teacher is `(-1,1,-2,2)`; the second is a nonidentical quarter-grid perturbation `(-1,5/4,-7/4,9/4)`.

| teacher | weight codec | model bytes | MSE | max error |
| --- | --- | ---: | ---: | ---: |
| planted | optimal two-block ternary steps `1,2` | 5 | 0 | 0 |
| planted | optimal shared ternary step `3/2` | 3 | 2/3 | 2 |
| planted | optimal shared sign-magnitude four-level step `1` | 3 | 0 | 0 |
| perturbed | optimal two-block ternary steps `9/8,2` | 5 | 5/48 | 3/4 |
| perturbed | optimal shared ternary step `25/16` | 3 | 59/96 | 7/4 |
| perturbed | optimal shared sign-magnitude four-level FP16 step `525/512` | 3 | 7919/65536 | 3/4 |

`exact.py` also exhaustively fits the standard asymmetric signed two-bit alphabets `{-2,-1,0,1}` and `{-1,0,1,2}` at the same three bytes. On the perturbed teacher, the latter attains MSE `383855/1572864`, better than shared ternary but worse than sign-magnitude. The four-level family selects its *best* scale among every finite FP16 value for each code tuple: the least-squares real minimum lies between two adjacent FP16 values, so its optimum must be one of those neighbors. The ternary family uses nearest codes for each step; code assignments change only at `s=2|w_i|`. Within each resulting interval the squared-error optimum is the mean of active magnitudes, or an endpoint. The script tests all such means and endpoints. Its chosen rational steps happen to be FP16-exact, so the rational lower bound is attained by the charged format. There are 81 explicit input evaluations per fitted map. No learned table is hiding in the three-byte charge.

The sign-magnitude alphabet `{-2,-1,1,2}` has no zero. It is a strong quality control, not a free native alternative: converting two-bit labels into signed dot operands has an instruction cost, as does converting ternary codes. Either reader needs an actual lowering before its rate and register use can be compared. A conventional signed three-bit fixed-unit code also represents the planted teacher exactly at two packed weight bytes; it is outside the equal-width two-bit comparison. This example establishes a conditional accumulator regime, not optimality among quantizers.

## The scheduling threshold, as a declared model

Take an output tile with `T` groups of 16 tokens and eight accumulator elements per group. Charge `R0=72` registers for all nonaccumulator state, 16 registers per group for one accumulator bank, and a cap of 256 registers per lane. A block-scaled implementation in the declared grammar retains both a live int32 partial and an FP32 output, so it needs `R_block(T)=72+32T`. A shared-scale implementation retains the int32 bank until the end and converts elements in place, using one temporary, so `R_shared(T)=73+16T`. At `T=8` these are 328 and 201; at `T=4` they are 200 and 137. For 128 tokens and a legal width choice of 4 or 8, the block program must launch two token workgroups per output row while the shared program may launch one. Assuming one independent weight fetch per workgroup, that is two versus one workgroup-level fetches of its respective packed image. This is a **feasibility and request-count model**, not a GPU time bound: cache hits, occupancy, operand decoding, the epilogue and bandwidth service can reverse a timing prediction. The two programs may also have different base registers. Nothing here certifies gfx1151 register allocation or elapsed rate.

For any row of length `K`, int8 activation codes and ternary weight codes have `|sum a_i q_i| <= 127K`. Both `K=5120` and `K=17408` are safely below signed int32 range; the whole-K integer accumulator is arithmetically feasible. The necessary scale identity is stronger: **every product in the accumulated row must have the same final scale**. A weight scale shared over K is insufficient if the producer still uses a separate activation scale in each 128-coordinate block. A single input-row scale, or a jointly constructed exact integer rescaling whose work is paid, is part of this candidate. Changing activation quantization may dominate the toy weight error on real model inputs. FP32 conversion once at the end also changes rounding order compared with per-block FP32 sums.

This is not a universal two-bank lower bound. It applies to the stated per-block integer-dot/FP32-drain grammar. One may serially spill partial outputs, use a wider or floating accumulator, decompose coefficients, or choose the four-level code. The two-bank result in the [scaled-FP16 study](../../../ffn/batched/compact-scaled/README.md) motivated the resource model; its measured eight-tile win is **not** a measurement of this proposal. The [resource-bounds framework](../../../discovery/resource-bounds/README.md) explains why an issue or register count becomes a hardware lower bound only after its machine premises are checked.

## Next decision

A worthwhile next experiment is a paired quantizer on actual producer activations and output rows: fit whole-K weight and activation scales jointly under a held consumer response constraint, then compare the best shared-scale integer reader against both the optimized block-scale integer reader and the best same-byte signed four-level reader. Count producer preparation, conversion and packed-code expansion, and compile register allocation before timing. If the matched control uses one accumulator bank too, the proposed regime offers no scheduling distinction. The exact toy identifies that failure mode without claiming a native speedup.

Reproduce from the Kelana root with `python3 research/isa-quantization/accumulation-regimes/exact.py`. The checked-in `results.json` is its output. The search is 81 ternary inputs, at most 256 code tuples per four-level alphabet and a few rational scale candidates per ternary region. This result belongs to exact rational map semantics plus an analytical, conditional resource model. It says nothing about a full model's loss or measured tokens per second.
