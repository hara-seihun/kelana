# Dictionary-native causal maintenance of the exact KIVI2 V interner

This is **one bounded storage realization**, not another quantizer or a native-attention speed claim. [`maintain.cpp`](maintain.cpp) takes the prior encoded state in its own arena and one arriving original BF16 K/V record, writes both chronological snapshots, and performs the scheduled K32/V33 flush **from the recent BF16 bytes currently in that arena**. The original quantized donor events are absent from the native process; [`audit.py`](audit.py) uses them only for independent acceptance. The bytes and the 256-token horizon are precisely those of [`../kivi-value-intern/`](../kivi-value-intern/README.md): same header, K sections, first-use V dictionaries, positional u8 references, packed 2-bit codes and FP16 min/step fields. No conventional K/V shadow, historical dictionary, hash table, old/new image pair, or full next image exists in the native maintainer.

## Declared capacity and boundary

The single **266,240-B statically reserved arena** is a contiguous address space with exact byte offsets. Insert/erase shift its own live suffix by `memmove`; the largest observed *used* length (including all intermediate shifts) is **263,429 B**. Three other static arrays are 12,288 B for eight key chunks, 2,048 B for swapping recent dictionary records, and 4,098 B for one chronological arrival. Thus fixed buffers reserve **284,674 B**, 20,094 B below the conventional KIVI2 304,768-B peak. The output snapshot is streamed through `write(2)` to an external acceptance consumer; it is not another resident image. The native process reads one event with `read(2)` and holds no stream/file/all-prefix buffers. The arena has **no application allocator, application page table, freelist, per-record allocator metadata, external fragmentation, or caller-owned page pool**; exact offsets and tail moves, not fixed-sized storage pages, provide addressing. Overflow fails explicitly instead of silently reallocating. The proven finite fixture panel fits; this fixed capacity is **not** a universal promise for arbitrary 256-token inputs (the format's worst-case unique-record size could exceed the conventional baseline).

The retained [`g++ 15.3 -O2 -fstack-usage` compile receipt](compile.txt) measures ELF `.bss` **284,800 B** (fixed arrays plus native globals), **768 B total initialized writable sections** (`.data` itself is32B; dynamic/GOT/init/fini sections account for the rest), and a maximum 4,976-B key-flush frame. Allowing **6,144 B** for its bounded call chain gives **291,712 B** of writable ELF plus stack before OS page rounding. Conservatively rounding BSS, data and stack to separate 4-KiB pages gives **299,008 B**. The executable also pays **6,053 B of `.text`**, plus PLT/init/fini and read-only metadata: GNU `size` reports9,607B in its aggregate `text` column. The three read-only/executable LOAD segments occupy16,384B of4-KiB pages. Including those pages raises this executable-plus-bounded-stack ledger to **315,392 B**, before shared dynamic-loader/libc pages. Code is shared across cache instances; it is not free or a per-instance value record. There is no compiled conventional-maintainer code comparator here, so the smaller writable-state result is not a total code-plus-data dominance result. The maintainer imports no heap allocator, and the external audit's source logs, conventional reference, model fixture and pipe are acceptance resources, not an inference cache. The baseline 304,768-B number is a cache-state budget rather than a measured whole-process RSS comparator. Therefore this realizes a **bounded lower maintained-cache working state** for these windows, not a total-system RAM benchmark or a general-capacity guarantee. It does not conceal a 305,029-B preallocation.

The K quantizer reads each current 32-token BF16 recent slab, converts BF16 to FP32 and computes per-channel min/max, division by three and nearest-even codes; the V quantizer reads the oldest recent dictionary record and computes four per-head groups likewise. Both write FP16 min/step and original packed codes. One quantized record is compared byte-for-byte against existing quantized dictionary entries and appended only on first occurrence. On removing the oldest recent reference, live dictionary records are reordered by first remaining use and unreachable entries are reclaimed. At most one 2,048-B record is staged for an in-place swap. The per-head K replacement retains existing K quant chunks and removes recent K, with no key shadow.

## Measured result and work ledger

Across the **8 train + 4 inspected-held** original 256-token windows, independently accepted **6,144/6,144 before/after prefixes**, **7,275,264 original logical record checks**, all final literal images, and all source/event hashes. Per-prefix canonical first-use ordering and every decoded K/V record are compared byte-for-byte by the separate Python decoder, which also compares its independently reconstructed entire image. Mean serialized peak remains **254,661 B train / 258,917 B held**, and maximum **263,429 B**. Native work totals **206,919 complete-record equality probes**, **3,361,880,540 bytes moved** in suffix shifts and dictionary swaps, and **12,642,048 bytes inserted** (including intermediate shifts and reinserted K chunks). Each per-window receipt records capacity, used peak, final bytes, comparisons and moves. The lower comparison count than the previous audit's 25,604,918 is the effect of incremental maintenance rather than repeatedly re-interning every prefix. Large move traffic is real; **no runtime speedup is claimed**. Reuse the original unchanged complete 16Q/8KV full-O receipts through exact ordered decoding, with held relative full-O squared error 0.003124373 and mean head KL 0.0761010; no model or observer was rerun.

Reproduce from this directory with `g++ -std=c++20 -O2 -Wall -Wextra -fstack-usage -o maintain maintain.cpp`, then `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /path/to/workspace/data/fish-s2-pro/venv/bin/python audit.py held-0` (substitute any of the 12 names), followed by `python aggregate.py`. Each window is independently sub-minute. The native executable and `.su` stack report are generated and ignored; successful aggregation removes them after the retained receipts are complete, so they do not obstruct managed-checkout release. The retained compile receipt owns the stack/resource measurements. Original fixture arrivals and donor event receipts stay in the linked directories. [`summary.json`](summary.json) and `*-result.json` are the retained acceptance and work ledger.
