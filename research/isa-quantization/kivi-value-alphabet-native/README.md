# Layer-0 four-level V alphabet: complete resident acceptance

**Completed fixed gfx1151 device acceptance and matched-boundary timing.** All four held windows passed complete pre/post physical and output acceptance; the four separately admitted timing stages captured 32 order-balanced matched boundary pairs. The candidate's median paired event ratio is **1.144× (slower)**, while its eight held actual complete-O states improve original teacher SSE by **9.52%**. This is not a full-model or average-token throughput result. The immutable candidate is the train-fitted positive four-level `../kivi-value-alphabet/layer0-alphabet.f32` (16 FP32 bytes); the original source, field bytes, K events, arrivals, eight retained held Q/teacher states, and full original O are unchanged. The [CPU candidate](../kivi-value-alphabet/README.md) improves original K2/V2 pooled held complete-O SSE by 9.52% with 16 B shared static cost; the stronger K2/V4 comparator pays about 57 KB more. No layer-1 native result or novel Q is claimed.

## Source and controls

`state.hip` uses the accepted cooperative no-shadow conventional K32/recent ring layout: eight 128-thread CTAs, exact original double-to-FP16 step converter, original K2 producer, and a group-owner per V33 flush. The mode-0 control chooses original nearest uniform digits from source BF16 extrema *before* rounding its FP16 low/step fields. The mode-1 candidate first produces the **same original fields**, enumerates four actual decoded FP32 values with separate multiply and add from the uploaded literal 16-B FP32 table, then compares squared FP64 distances to source BF16, choosing the smallest label on exact ties. It packs only four-level codes into otherwise identical 48-B V records. No prepared quantized event is uploaded. `reader.hip` uses the candidate's four-word table for each aged V coordinate with separate FP32 product and sum; its 16Q/8KV attention, recent reads, complete 1024-O projection and two Q positions reuse the cooperative original reduction geometry. The control reader has the original FMA digit reconstruction. Both arms are in one module, with mode branches in the common V33 producer. There is no feedback/moment state.

For each of four held arrival streams, the native host creates a **fresh empty** cache for each arm, appends only BF16 K/V arrivals t1…256, snapshots immediately before the query/flush and after K32+V33 at every step, and reads the *original* held Q only at t128/t256. Mode 0 precedes mode 1 in acceptance. After all four audited acceptances, timing has four fresh rounds per held stream with order `(window+round)%2`, for **32 order-balanced matched t128/t256 arm pairs**. Each raw timing output is saved alongside its raw spans; the complete 256-step replay and setup/teardown are separately reported. No average-token, different placement, alpha or precision ladder is inferred from those boundary samples.

## CPU physical proof, device acceptance and timing

`cpu_precheck.py` runs the separately maintained original physical CPU replay from independently pinned arrivals, then substitutes **only** candidate records from the frozen candidate event files in mode 1. `audit.py` checks all physical pre/post K bytes, aged V field/code bytes, recent V ring bytes and per-head logical prefix hashes against two independent owners: original `kivi-two-bit-causal` control manifests and candidate `kivi-value-alphabet` per-prefix manifests. For four held windows, 4,096 frames, 4,358,144 ordered-record checks, and 917,504 candidate flush-coordinate/code checks pass. The four `cpu-audit-held-*.json` receipts pin raw physical stream SHA/size. `score.py` independently decodes the candidate's original saved per-prefix images with the *physical* 16-B table and original Q/O; eight complete-O targets match the upstream candidate output hashes and are saved as `held-*-t*-alphabet-cpu.f32`. `prelaunch.py` checks all fixture/source/table/image hashes and the compiled resource bill without a device call.

Four independently admitted device acceptances checked **4,096 actual pre/post images**, **4,358,144 original ordered records**, and **917,504 candidate flush-coordinate/code checks**, against both independently owned event/prefix sources. Their raw 1,249,951,744-B snapshot streams are retained losslessly as four `.bin.zst` files, with raw and compressed SHA in `audit-held-N.json`. All 16 acceptance complete-O outputs pass their **own** control/candidate CPU target with maximum coordinate error ≤1.431e−6 and relative L2 ≤8.605e−7 (guards ≤0.005). Actual pooled teacher SSE across the eight held states: **0.8326574748 control** and **0.7533859211 candidate**. Bonsai remained active at PID **145247** before/after all eight one-attempt stages; every marker was consumed. No denial, retry or service change occurred.

The combined **1.144× is the median of 32 individual candidate/control ratios, not a ratio of medians**. None of the 32 candidate event spans is faster; the range is 1.087×–1.357×. Across all 32 samples, median control/candidate input H2D spans are **16.339/16.474 µs**, compute spans **68.938/81.317 µs**, and post-validation host wall spans **164.434/170.814 µs**. Event spans include arrival/Q transfers, append, complete Q→K/V/O, and K32+V33 flush; they exclude preparation and audit snapshots. The wall span additionally includes post-event error D2H, actual-O D2H, output-file write and CPU guard—**it is not pure serving latency**. Median full-256 replay wall across 16 fresh traces/arm is **8,572/9,266 µs** control/candidate, and median full arm allocation→teardown wall **9,032/9,672 µs**. Candidate's setup allocates/uploads its literal 16-B table. Original O H2D is common shared setup, 45,690–52,345 µs per timing window; shared teardown is 117–165 µs. These are four-window resident boundary measurements, not unobserved Q positions or full-forward runtime.
