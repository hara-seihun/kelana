# SKVQ primary-source correspondence and one paid Qwen causal comparison

This is a **source-mathematics correspondence and single frozen packed CPU comparison on one head-local GQA group**, not a claim that the prior [train-RMS-folded KIVI](../kivi-v-channel-fold/README.md) is SKVQ, that this isolated-head adaptation is the official full-model SKVQ method, or that it is a native result. The literature is Duanmu et al., [*SKVQ: Sliding-window Key and Value Cache Quantization for Large Language Models*, COLM 2024](https://arxiv.org/html/2405.06219v3), especially §3.1–3.2. Official [cat538/SKVQ](https://github.com/cat538/SKVQ) was read from immutable Git commit **`fdfc7ec315c16293f68dd771850b47f5199787fc`** in a managed read-only checkout; upstream LICENSE is MIT. Source locations below refer to that commit. Its README explicitly says the reported results used **fake quantization** and that the current dequant/GEMV kernel is naive/inefficient. A CPU port must not be presented as upstream-native speed or paper reproduction.

## What upstream actually serves

* [`calibration.py:get_reorder_indices`](https://github.com/cat538/SKVQ/blob/fdfc7ec315c16293f68dd771850b47f5199787fc/calibration.py#L241) collects per-channel projection-output minima and maxima, fits separate KMeans with `n_init=10` to 2D `(min,max)` features for K and V, orders by cluster label, and retains *unequal-size cluster boundaries*. It does **not** sort by channel RMS, force equal 32-channel groups, or choose a permutation by complete-O error. Official `ModelKVCacheManager.create` sets `hidden = cfg.num_key_value_heads × cfg.hidden_size // cfg.num_attention_heads` (which equals KV heads ×head_dim for its supported Llama/Mistral models) and its calibration clusters **all K and V layer channels globally**, not per KV head. Qwen3-0.6B's configuration is `hidden_size=1024`, `num_attention_heads=16`, `num_key_value_heads=8`, **independent `head_dim=128`**; the actual K/V projections are 1024 output rows, whereas the unmodified upstream formula would infer only **512** and trip the `num_heads*head_dim==hidden` source assertion. Our reader sets the actual one-KV-head width128, a required Qwen wrapper adaptation. Qwen3-0.6B layer0 has 8 KV heads ×128 coordinates; full-layer 32-cluster grouping may cross head boundaries and cannot generally be evaluated as an independently encoded single-head 128D table. This study deliberately restricts clustering/packing to one complete 128D KV head and its two Q consumers, a **local boundary adaptation**. Its command-line calibration runs other model families and much more calibration data than the local Qwen fixture; a Qwen transfer must name its changed producer and sample policy.
* [`KV_process.py:quant_pytorch`, `quant_cuda`](https://github.com/cat538/SKVQ/blob/fdfc7ec315c16293f68dd771850b47f5199787fc/KV_process.py#L92) and [`kernels/csrc/quant.cuh`](https://github.com/cat538/SKVQ/blob/fdfc7ec315c16293f68dd771850b47f5199787fc/kernels/csrc/quant.cuh#L75) quantize **both K and V per token**, by KMeans cluster: each group uses signed min/max multiplied by a common positive clipping factor α, stores `origin=α min`, `step=max((α max−α min)/(2^bits−1), 1e−5)`, clamps/rounds codes and independently stores scale/origin. The packed CUDA path uses 2-bit codes in uint8, **high-significance code first**, with `ceil(cluster_width/4)` bytes **separately per group**; unequal groups therefore cost packing padding. It stores scale/origin in FP16, or in optional FP8 for the `-fp8` arm. The CUDA arithmetic takes FP16 input, reductions/clip/step in half, rounds to integer, then decodes FP16 fields. A faithful CPU numerical correspondence must state half rounding, not silently replace it with KIVI's FP32 min/max followed by FP16 fields. The upstream PyTorch fake path likewise quantizes/dequantizes immediately; it is not a paid cache image by itself.
* [`KVcache_manager.py:SlidingKVCacheManager.forward`](https://github.com/cat538/SKVQ/blob/fdfc7ec315c16293f68dd771850b47f5199787fc/KVcache_manager.py#L158) holds **unquantized first sink tokens**, per-token quantized middle, and **unquantized newest W tokens** for both K and V, shifting the oldest window token to the quantized middle as the next token arrives. The [`eval_needle.py` parsing contract](https://github.com/cat538/SKVQ/blob/fdfc7ec315c16293f68dd771850b47f5199787fc/eval_needle.py#L558) uses `-clip` = **0.92** (one uniform scalar for all groups), `-sink5`, `-pre_rope`, `-reorder` tied to the calibration file, and supported group/window choices 32/64/128. Its README sample uses 2/2-bit, group128, window128, sink5 and pre-RoPE; a smaller window/group is a supported source setting but is **not** the paper's selected full-model result. The original Qwen causal observer must retain all 256 keys including sink; a sliding *precision* window is not a local-attention mask dropping old tokens.
* The serving [`experiments/modeling_llama_skvq.py`](https://github.com/cat538/SKVQ/blob/fdfc7ec315c16293f68dd771850b47f5199787fc/experiments/modeling_llama_skvq.py#L417) appends current K/V to the manager before the current query, dequantizes old code, and applies RoPE after cache reading when `pre_rope=True`. Its model implementation supports Llama/Mistral, not Qwen3 with K/Q RMSNorm; Qwen transfer must quantize the actual **post-Knorm/pre-RoPE** K source so RoPE is applied after decoding, while Q and V/O stay the canonical Qwen teacher. Otherwise it silently changes teacher scores. The official `reorder_weight` helper in `KV_process.py` is defined but has **no call in this checkout's evaluation path**; the official CUDA pack/gather and inverse-scatter dequantization actually consume K/V permutation indices. Physical V/O folding is our separate equal-byte construction, not something to attribute to this official serving path. Pack/dequant carries the K/V permutations and cluster boundaries as per-model fields; treating the calibration checkpoint as free metadata is invalid.

## One predeclared near-rate configuration and its realized image

**Proposal sent to the coordinator before fitting:** head-local 128D one-KV/two-Q-head Qwen group, 256-token causal prefix; K/V **2/2 bit**, nominal `gsize=32` = four `(min,max)` KMeans clusters per each 128D vector, `window=64`, `sink=5`, `pre_rope=True`, clipping α=`0.92`, half scale/origin, no FP8 or smoothing, no heavy-hitter eviction. For reproducibility in this **Qwen adaptation**, use only the existing 2,048 training capture rows and fixed KMeans `n_init=10,random_state=0`; K stats are actual post-Knorm/pre-RoPE source, V stats are BF16-projected source. This is a necessary changed-calibration/model **and head-local clustering** adaptation, not the exact official whole-layer calibration workload. In official whole-layer calibration, KMeans may assign channels from different KV heads to one cluster; sharing one global packed code group would then require source values from multiple heads. Without encoding the other seven heads or choosing a head-local grouping as here, a 128D-only packed image would be an invalid official full-layer result. The declaration preceded all source preparation, KMeans fit and candidate scores. No subsequent bit, window, clip, group, calibration seed, or image choice was made. The realized K cluster widths are **28,1,1,98** and V widths **51,23,35,19**, in stored cluster-label order, not four equal 32-wide groups. Their exact 532-byte int16 descriptor is [`source-descriptors.bin`](source-descriptors.bin) (SHA256 `fd7398858dcda38110628f0e7ae9e8bfccf40fa23ce7d662c732caa62ed96864`); [`source-descriptors.json`](source-descriptors.json) records all source features' hashes, actual indices/bounds and training policy. Each K old-token code uses **34 B**, V **33 B**, and each side needs **16 B** for four FP16 origin/step pairs: 50+49 =99 B per aged token. The two singleton K clusters still receive scale/origin pairs and their own padded packed byte each; they are not silently dropped or merged.

At prefix 256 the manager has five shared sink +64 newest recent = **69×128×2 bytes ×K/V =35,328 B**. Its 187 older tokens need **187×[Σ₍g=1…4₎ ceil(K_width_g/4) + Σ₍g=1…4₎ ceil(V_width_g/4) + 2×4×2×2] bytes**: each of K and V carries 32–35 code bytes and four FP16 (origin,step) pairs =16 B per token. This is **17,952–19,074 B** across K+V; actual exact point depends on the once-only train KMeans memberships and must be stated after those are computed. The official on-the-fly reordered pack/inverse-scatter path has **two 128×int16 permutation arrays =512 B** and **two five-entry int16 cluster-boundary arrays =20 B** static per-model, charged **once**, not per token. Total model-specific incremental state **53,812–54,934 B** at this boundary, including these 532 B; actual **resident 54,373 B**: `187×(50 K+49 V)=18,513` old bytes + `5×512=2,560` sink + `64×512=32,768` recent +532 descriptors. On arrival of the 256th token, the current manager temporarily holds **65** recent before aging the oldest: `186×99 + 5×512 +65×512 +532 = 54,786 B` **causal high-water**; the sink/window BF16/FP16 width is two bytes in either case. KIVI G32/R32 is 52,400 B, the pinned query-metric cache 54,704 B; total bytes alone are not a quality/work ordering. Generic shared CUDA/CPU pack code is program state outside per-model bytes, while calibration-statistics/checkpoint files are offline artifacts not additionally retained once those 532 B descriptors suffice. The baseline Q/K/V/O/gamma BF16 weights remain common, unchanged for this head-local, official-kernel-math Qwen transfer. The 532 B descriptor is **all of this isolated model's** two 128D permutations/boundaries, not a free one-eighth share of a hypothetical global permutation. No 786,432 B physical source replacement or free folded permutation is assumed.

The dynamic work is a different algorithm than KIVI: at each aging token, 2×4 group reductions over up to128 K/V coordinates, clipped FP16 scale/zero and128+128 nearest/clamped assignments, then packed writes; the first five and latest64 use FP16/BF16 full vectors. On reading a 256-token prefix, old K/V codes/fields need group unpack, FP16 dequant and inverse scatter; **pre-RoPE** requires applying positional RoPE to decoded K rather than simply using KIVI's once-rotated cached keys. Both Q heads share one K/V cache, then each performs the usual full causal score/softmax/value mix and its own complete O. The repeated pre-RoPE replay touches `Σ(t=1…256)t×128 = 4,210,688` K coordinate rotations per window if performed literally, compared with KIVI's once per inserted token; the requisite Qwen RoPE frequencies are existing model/generic program parameters, but caching both 256×128 **BF16** cosine and sine grids would occupy **131,072 B transient/live scratch**, which is *not included* in the compact retained cache and is not required if recomputed. The current CPU reader materializes up to 256×128 FP32 K and V arrays, at least **262,144 B transient scratch**, plus score/output arrays and temporary RoPE grids; no native latency or sustained throughput is measured. [`build.py`](build.py) emits an immutable byte image and a timestamped event log for every training/held window; [`replay.py`](replay.py) independently parses the descriptors, packed 2-bit fields, FP16 scales/origins, five original sink tokens and BF16 recent windows. Every causal insertion and before/after-aging state has an exact byte length/SHA receipt. It checks each emitted K/V code and origin/step against only that source token when aged; the event log is evidence, not extra live state. The reader carries both original Q heads, re-RoPEs each decoded pre-RoPE K at its original position, and applies the original shared V and both full O column blocks. All **8 train +4 inspected-held** windows and their final images/event logs are in this directory; [`results.json`](results.json) requires every original-teacher/descriptor/image check and aggregates actual SSE/reference-square sums, not window relative means.

The Qwen BF16 post-Knorm/pre-RoPE recent-key cast is a named adaptation (official Llama serving uses FP16). Re-RoPE after this uncompressed cast differs from the canonical FP32 post-normalization/pre-RoPE teacher by as much as **0.9921875** in an individual rotary key coordinate, but original-teacher complete-O round-trip error before *any* 2-bit quantization is only **1.7184e−6 train / 1.3851e−6 held** relative squared. Original Q/K/V/O/gamma and teacher logits/output are checked at `<1e−4` maximum absolute difference before scoring. Thus the large 0.00805 held error is not explainable merely by this BF16 recent-key source boundary; it is the frozen local low-bit arrangement's observed complete response. This does **not** rank published full-model SKVQ against KIVI: methods differ in bits, key allocation, model architecture, head-global versus head-local clustering, original calibration volume and observer. A complete SKVQ source boundary needs all eight KV heads and all sixteen query/O consumers calibrated and encoded jointly; a separate full-layer study owns that requirement. No held-based reconfiguration follows.

## Exact source/interface boundaries after implementation

1. The official trainer collects projection-output K extrema *before* any Qwen-specific K RMSNorm; using those extrema to cluster actual post-norm/pre-RoPE K would be mismatched. Choosing the latter is explicit architecture transfer, not an exact upstream Qwen path (there is none).
2. Upstream serving uses CUDA half tensors and a Llama/Mistral RoPE path; Qwen's BF16 projection, BF16 internal RMSNorm/gamma, FP32 RoPE teacher and cache recent width differ. Preserve the canonical Qwen source producer and name whether packed half conversion or recent BF16 is used. Matching the original score is a separate source acceptance check before evaluating loss.
3. `fake_quant=True` is the default model evaluation and cannot establish packed-byte rate. The packed CUDA `fake_quant=False` path is present; its source-indexed CPU mathematical port here independently serializes/reads fields and bytes, including cluster-by-cluster padding and stored half-origin/step arithmetic. Avoid importing its Llama model wrapper wholesale or claiming GPU kernel performance.
4. At `t=256` the manager update happens **before** reading current attention. Sink5/window64/old187 are simultaneously live; the reported 54,786 B causal pre-aging high-water is distinct from any allocator copies/transient CPU arrays beyond it; these are not a native process-memory census. The original KIVI source read keeps different recent flush chronology. This construction is comparable-size and complete-observer, not exactly equal byte-for-byte method timing.
