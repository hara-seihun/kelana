# Can the E8P/RVQ block dot stay packed?

The [stored QuIP# E8P12RVQ3B rank-zero image](../quip-e8p-local/README.md) is 6,178 model-specific bytes, with 1,024 B E8P absolute and 4,096 B E81B FP16 generic tables shared among layers. This CPU-only study examines its **complete eight-coordinate block dot**, rather than pretending that a stand-alone code lookup or a syntactic GPU kernel rewrite is the endpoint. The [native endpoint](../quip-native-endpoint/README.md) and the held response panel own their measured results. We did not run the GPU for this question.

## Exact coordinate identity

For code `c=(h<<8)|s`, let `n_j(h)` be nibble `j` of the 1,024-byte E8P absolute table under permutation `(0,4,1,5,2,6,3,7)`, and `p=(-1)^popcount(s)`. Define `e_j=(-1)^(bit_(perm[j])(s xor parity(s)))`. The exact lattice vector has `q_j^E8=(n_j-8)e_j/2+p/4`. Each stored RVQ byte `r` selects `g_j(r)` from the fixed residual grid; inspection of **all 256×8 FP16 entries** shows `2g_j` is an integer in `[-4,4]`. Thus the real-number block dot for dynamic transformed input `z∈R^8` is

```text
B_j(c) = 2(n_j(h)-8)e_j + p             (signed integer, image range -11..11)
G_j(r) = 2g_j(r)                       (signed integer, table range -4..4)
block(c,r,z) = (B(c)·z)/4 + (25/102)(G(r)·z)
```

The denominator `25/102` is exactly `(1/2)/2.04` **in real arithmetic**. The image's global FP16 scale is applied after block reduction. This is a *two-integer-dot coordinate system*; it does **not** make the residual term disappear or make `B` a free instruction. `study.py` reconstructs the existing stored image from those two independent coordinate maps, runs the input sign/Hadamard and output Hadamard/sign, and compares all **1,024 real held producer states** against the independent float64 stored-image decoder. Maximum absolute response discrepancy is **1.34e-15**. Different FP32 rounding orders are not bitwise identical by this real-number identity.

For arbitrary float inputs, expressing both terms in the `B,G` coordinates still needs all eight independent products per term, or a separately priced input-dependent table. In particular, four dot4 integer instructions cannot consume float32 `z`. Merely unpacking the image into eight signed byte `B` values and calling a float dot does not by itself reduce work; it exchanges eight float coefficient reconstructions for eight byte fields and two eight-term dot products, plus the same dynamic transforms. The residual FP16 table is not a hidden zero-cost signed byte: the committed [`e81b-twice-i8.bin`](e81b-twice-i8.bin) is an **exactly equivalent 2,048-byte generic replacement** for that 4,096-byte reader asset, with hash in [`results.json`](results.json). If both generic assets must coexist, add 2,048 B of resident storage rather than claiming a saving.

## A nearby integer producer/consumer map, priced

The pinned [gfx1151 instruction index](../../../hardware/gfx1151/INSTRUCTIONS.md) has signed `V_DOT4_I32_IU8` (alias `V_DOT4_I32_I8`) for four packed signed byte pairs with integer accumulation. If an upstream producer *already supplies each transformed eight-vector as signed int8 `b` with a shared per-block scale `α`*, the **real-number** output block is `α[(B·b)/4+(25/102)(G·b)]`. Two dot4s for `B`, two for `G`: **four dot4s per block, 8,192 per 128-output input row**. The row still requires 16 blocks of code/lookup, 16 partial-pair scales, reduction and two live 128-point Hadamards (448 butterflies/896 scalar add-subs each), as well as both sign masks and the global FP16 scale. A dot4 reduces the multiplication stage, **not** the full reader automatically.

Producing that label from this experiment's ordinary FP32 Qwen input is not free: first apply the entire signed input Hadamard, then calculate **16 FP32 symmetric group scales** `α=max|z|/127` per state, round and pack 128 int8 transformed coordinates. After four integer dots per block, convert both int32 accumulators, apply `α/4` and `25α/102`, sum 16 block outputs and apply the output transform. Each consuming row must also derive eight `B` signed bytes from packed absolute nibbles, eight code sign bits and parity (or buy a prepared model-specific B image), read eight `G` bytes by RVQ index, and pack each pair of four byte operands in its required lane layout. No emitted kernel, register allocation or speedup has been established for this alternative. The existing native QuIP kernel uses **91 VGPR / 32 SGPR** and zero scratch; this map needs at least the two integer accumulators, packed operands and dynamic scales per active lane, but its actual register count is unknown until lowered.

On all 1,024 held states, the CPU int8 post-Hadamard control gives relative squared teacher-response error **.006681875** against the exact QuIP image's **.006671714**, with maximum absolute response difference **.004955**. The matched 6,176-byte scalar stored-image control has full held error **.010877023**. This small extra distortion and the 2,048-byte generic asset do **not** establish a native advantage: the label preparation, 8-byte base-vector generation per block and reductions can outweigh the packed arithmetic. It is exact *conditional on receiving the declared byte+scale label*, approximate relative to the original FP32 producer states. If bytes arrive **before** rather than after the 128-point Hadamard, the integer transform can grow to 128 signed-byte contributions and is not guaranteed to fit int8; rounding/renormalizing or an int16 consumer is a new paid boundary.

A fully prepared signed-byte `B` image would consume **16,384 B model-specific** for 2,048×8 bytes in place of the current 4,096 B E8P codes; retaining residual codes (2,048 B), signs (32 B), and scale (2 B) produces **18,466 B** rather than 6,178 B. This separately priced prepared route would avoid live base nibble/sign reconstruction, but cannot serve as a matched-image win. Precomputing a dynamic full-E8P-code dot table per input is another explicit alternative: 65,536 codes ×16 input blocks ×4 B = **4,194,304 B transient**, plus 256 residual dots ×16×4 B = **16,384 B transient** and their preparation arithmetic, before per-image lookup and output transforms. Computing only the codes actually used by this one image does not make the table attractive: 2,043 of the 2,048 `(column block,row)` E8P codes are distinct at their own block position. The image has 1,985 distinct `(absolute,residual)` pairs; the table cannot be assumed reused across rows. These are cost observations, not an ISA lower bound.

An upstream producer could carry the byte+scale transformed label into several compatible readers and amortize its 16-scale preparation; that is the concrete continuation that might change the execution ranking. It would require a source-level operator contract specifying the label and downstream acceptance, plus **all** consumers' numerical effects, before comparing to the scalar control. For this local independent FP32 input and 128-output projection, there is no demonstrated work saving or native speedup. The finite identity and the paid near-map delimit a discriminating future kernel comparison; they do not replace it.
