# E8P combinatorial magnitude: complete reader, compile-only gfx1151 screen

This is a **lowering and storage discriminator, not a GPU timing or numerical-endpoint measurement**. The frozen source is the full 128×1024 Q row in [`../e8-main-program/`](../e8-main-program/), recoded image SHA-256 `6b2f5c60ed0ef30139a824263711264550b4f2ec03a8abe2b2835f47ba782e8d` (49,327 B), from root image SHA-256 `d39500d3a5fbfd3260f4139d064ab00654582e15e4fc461fc923502d841f907a` (50,322 B). The 49,298 model-specific bytes are unchanged in size, although the high bytes of 16,384 main codes have been relabeled. Generic data changes from the old 1,024 B magnitude table to 29 exception-mask bytes. All source weights and real-arithmetic main dots are equal according to the source study's complete replay. Its response quality therefore does not change. No new quantization, fitted labels, activation approximation, GPU admission, kernel execution, or serving adoption occurs here.

`reader.hip` compiles three **complete** readers in one translation unit with the same input sign field, 1024-wide input Hadamard, 16,384 main+root-residual blocks, half scale, 128-wide output Hadamard and output signs. Root residual bytes are decoded from their original signed-root coordinates in **all three** arms; they are not a residual table. One block of 128 threads produces 128 outputs for each dynamic 1024-input item. The original arm uses its stored magnitude table and old labels. The direct arm computes the colex threes-mask from a new high-byte label, reads the 29 exception bytes only for labels 163–191, computes the optional five index, signed half-root base, sparse 3/5 corrections and odd-three slot-7 sign correction, and folds in the quarter-offset input sum. The prepared arm computes a 1,024 B *new-label* magnitude table **once on the host**, transfers it to a persistent device allocation and uses the established hot-table reader on the recoded codes; it never reuses an old-label table against new codes. `labels.hpp` is the shared device/host decode, not a shipped extra table. The original full-root reader from `../quip-full-native-root/native.hip` has the same 3,056 B kernel body and 10,872 B out-of-line transform helper in its emitted baseline.

## Emitted and resident byte ledger

`./build.sh` uses `hipcc -O3 --offload-arch=gfx1151 -save-temps -c`; [device ISA](assembly-gfx1151.s), [host assembly](assembly-host.s), and [raw symbol/resource receipt](compile-receipt.txt) preserve this exact lowering. `llvm-nm -S` of the device executable measures body bytes, *not* assembly file length. All three have 44 VGPR, 33 SGPR, 4,608 B LDS, zero private scratch, 32 B kernargs, the same shared 10,872 B input-transform helper and an inlined output transform. Each has a distinct 64 B kernel descriptor and comparable 138 B host stub; these equal components and the HIP runtime are outside the differential totals.

| complete reader | stored image | persistent extra GPU bytes | device kernel body | helper | image + resident extra + device body + helper |
|---|---:|---:|---:|---:|---:|
| original root + hot magnitude table | 50,322 | 0 | 3,056 | 10,872 | **64,250** |
| combinatorial direct whole-dot | 49,327 | 0 | 4,700 | 10,872 | **64,899 (+649)** |
| combinatorial prepared hot table | 49,327 | 1,024 | 3,036 | 10,872 | **64,259 (+9)** |

The direct kernel costs 1,644 B more code to save 995 B generic data **once per shared reader pool**. The prepared kernel is 20 B shorter because its table is a separate pointer, but its 1,024 B live GPU allocation exceeds the saved 995 B; it also needs transient 1,024 B host stack storage and 1,024 B host→device transfer at preparation. Emitted x86 host preparation is `prepare_magnitudes` 858 B, `prepare_device_magnitudes` 99 B, `release_device_magnitudes` 5 B; launch wrappers are original/direct 213 B each, prepared 217 B. This adds 962 B host preparation/release code (and a 4 B launch-wrapper delta) beyond the GPU static ledger, before any common allocator/runtime code. These are actual complete-symbol byte lengths, not a HIP binary/runtime census. The prepared hot reader makes one 32-bit magnitude load per block (16,384 logical loads per batch-1 full Q row), just as the old reader does, but additionally pays preparation. The direct reader instead loops over eight colex decisions per code plus conditional mask corrections; 12,785 labels are small subsets, 687 use exception bytes, and 2,912 contain a five in this *frozen* image. Input/output transforms, root residual and other fields remain paid. There is no evidence that instruction bytes predict latency; no speedup or runtime loss is claimed.

Static code+resident-data **does not win** in either of these straightforward realizations. Even across many matrices sharing one reader, both generic data and kernel body are charged once, not once per matrix. A separate serialized-storage objective can still value the 995 B smaller persisted generic description with preparation paid elsewhere. This screen does not rule out a different lower-ISA map fitting below the 995 B incremental body budget; it says these concrete complete maps do not earn that static saving. The direct float accumulation reassociates the old per-coordinate FMA reduction; exact coefficient maps do not establish bit-identical FP32 output. A native acceptance run would have to check this if that realization were advanced.

## Reproduction and exact CPU controls

From this directory, `./build.sh` produces the emitted assemblies and symbol/resource receipt. `python3 check.py ../e8-main-program` compiles the same host label program with `g++ -O3`, prepares all 256 entries and compares each nibble against the independent parent decoder; it also checks 2,816 complete main dots (256 labels × 11 low sign/parity codes) against the independent main-vector formula, including odd-three slot-7 corrections. Receipt: `prepared_bytes=1024 exception_bytes=29`; `labels=256 exact main_dots=2816 exact`; image SHA as above. The source study separately checked all 65,536 main words × 8 basis coordinates and complete decoded-weight equality. Neither CPU check simulates hardware FP32 evaluation order or certifies runtime latency. Generated `emit/` is disposable; source, complete emitted host/device assembly and compact receipt are committed here. The parent owns the source image/decoder and common research catalogue.
