# Frozen layer-1 contextual value-feedback transfer

**Result: no transfer of the layer-0 gain at this declared CPU boundary.** Across all 256 causal queries in each of eight original train and four inspected validation windows, the unchanged first-order KIVI2 V-feedback rule **increases** original-teacher full-O pooled SSE by 14.70% train and 11.58% validation relative to original K2/V2. Original-code V delay2 uses **768 B less peak state** than feedback and has lower error; unchanged higher-rate K2/V4 also has lower error. Feedback still wins 297/2048 train and 213/1024 validation individual queries against original K2/V2. There was no fit, gain, filter, rank, precision or order selection after the source/arm contract. This is a **teacher-forced original layer-0 residual → layer-1 CPU producer/observer**, not a rollout of the layer-0 feedback cache into layer 1, an original GPU layer-1 capture, native execution, or a full-model result. Layer-0 feedback's separate retained eight-state gain is not contradicted.

## Original source and explicit arithmetic boundary

[`contextual-value-sharing`](../contextual-value-sharing/README.md) owns the original Qwen3-0.6B BF16 checkpoint SHA256 `f47f71177f32bcd101b7573ec9171e6a57f4f4d31148d38e382306f42996874b`, token fixture SHA256 `0479292cbee2cfc6cfc5f89e8f85dac85d2c0c275ed2704a59a7006faa7d66a2`, original complete teacher-layer-0 post-residual capture SHA256 `aa1e671af9283656efd7a95f2732a27662ce8c658766af5ee88f5e7d27b9e69c` and recovered original capture-producer SHA256 `42eae1e97b1a5a609022f62df15770c6f9ffb10505e46dcbc7987c74ffa5883d`. Checkpoint revision `c1899de289a04d12100db370d81485cdf75e47ca`. The captured `train_teacher_post` and `validation_teacher_post` slices `[256*w:256*(w+1)]` are the genuine original BF16 post-layer-0 residuals after both attention and MLP, fed as independent position-0…255 histories to layer-1 input norm. The original native/GPU layer-1 forward, Q and teacher were **not** captured. The token fixture identifies those histories but does not recompute their residuals.

The **single fixed CPU observer** decodes each captured BF16 residual to FP32, computes per-row FP32 RMS with `epsilon=1e-6`, BF16-rounds normalized values (nearest even), multiplies the original layer-1 input gamma in FP32 and BF16-rounds. This exact input norm and layer-1 V projection use the existing sharing owner's NumPy/one-thread BLAS operation order: FP32 multiplication by original BF16-decoded 1024×1024 V weights, BF16-round the output. The same **byte-identical normalized input** is fed to one-thread Torch FP32 matmuls by original BF16-decoded 2048×1024 Q and 1024×1024 K weights; Q/K projected outputs are BF16-rounded. Original layer-1 Q and K norm gammas operate separately on every 128-D head: FP32 RMS with the same epsilon, BF16-rounded normalized activation, original gamma multiplication in FP32 then BF16-round. Position 0…255 RoPE uses base `1,000,000`, split halves `(i,i+64)`, BF16-rounded sine/cosine and FP32 rotation. Q remains FP32; original FP32 rotated K goes into the **declared CPU full-attention teacher**, while K is BF16-rounded *after RoPE* for the recent K cache and quantizer. Original BF16 V is shared by teacher and all arms. All 16 Q heads address 8 K/V heads two-to-one, FP32 causal scaled logits/softmax and weighted V, then the original BF16 1024×2048 full O as FP32 matrix multiplication. The reference does **not** round mixed attention/O output to native BF16. This is an explicitly new CPU rounding boundary, not a claim of bitwise GPU layer-1 identity.

Prior source correspondence was checked **before any arm encoding**. An initial Torch V trial differed at 46/262,144 BF16 coordinates for train0 against the existing sharing owner's NumPy V operation order, although its 256 packed records were equal. It was rejected and not used for any arm. The frozen final producer uses the owner's NumPy norm/V order for all rows, with **BF16 V and full-eight-head 384-B packed G32 V byte-exact in all 12 windows** by the independent [`custody.py`](custody.py) replay of the owning [`screen.py`](../contextual-value-sharing/screen.py) rule. The source Q/K use the same resulting norm bytes; Torch's alternate norm would differ by 13 BF16 input coordinates in validation3 and zero elsewhere, so silently substituting it was disallowed. [`custody.json`](custody.json) records each V/packed hash and the owner receipt hash; the owner receipt stores counts rather than raw V arrays. We reproduce its rule and hash the reconstructed arrays, not falsely attribute these new hashes to an earlier stored file. Each saved source NPZ records residual, token IDs, **original CPU** Q, BF16 K, BF16 V and FP32 full-attention teacher exactly once per window, with individual array hashes and original input/producer identities in `*-source.json`. The common original layer-1 BF16 O tensor was exported once as [`original-o.bf16`](original-o.bf16), with original checkpoint SHA, tensor shape/bytes and O SHA in [`original-o.json`](original-o.json); every source receipt now links this O hash, and independent replay decodes only that SHA-checked owned tensor rather than reading mutable model weights. This custody link was added to successful source receipts without rerunning their numerical outputs: the original checkpoint file hash had already been checked by the source producer, and the new O bytes were extracted from that same SHA-pinned checkpoint. The source used for these artifacts is preserved byte-for-byte at [`sources/1f8f577a66b338e60576c8f13b799b85943423793bac22ee9f7f8f95fdc359f7.py`](sources/1f8f577a66b338e60576c8f13b799b85943423793bac22ee9f7f8f95fdc359f7.py); the receipt provenance links were appended without recomputing numerical source. Current `prepare.py` snapshots its own bytes before touching model inputs and pins the O tensor at source preparation.

A separate **source-only BF16-K and CPU reduction-boundary sensitivity** reads the identical stored Q/V/O and replaces the teacher's FP32 rotated K with the BF16-rounded K *without quantization*: pooled SSE **0.038507522 train**, **0.018142388 validation**. The saved teacher was computed by batched full-panel bmm/O, whereas the independent replay uses individual-query bmm/O; this control therefore also contains floating accumulation-order differences and does **not** mathematically isolate K rounding. It is not folded into a quantizer improvement claim. The much larger four-arm errors are downstream of paid compression and accumulation, not simply evidence of that combined source boundary.

## Causal arms, evidence, and costs

At each original arrival/query, K holds up to 32 recent BF16 tokens, then flushes a 32-token chunk after the query; V holds up to 33 recent BF16 tokens, then flushes its oldest after the query. Original K2 is per-channel across a time chunk, and original V2 is per-token/four contiguous G32 groups. FP32 extrema of the *source BF16* values yield `(max−min)/3`, nearest-even unsigned two-bit digits, and FP16 origin/step fields. K2/V4 changes only V to four-bit digits and source divisor 15, keeping original fields width, K and chronology. Original-code V delay2 waits for 35 recent V tokens after the query (same original V codes and fields, emitted two timestamps later). The unchanged feedback rule from [`kivi-value-error-feedback`](../kivi-value-error-feedback/README.md) has a zero-initialized FP32 128-coordinate residual **per KV head**. On each original t33…256 V flush, retain the **unshifted source** group extrema and FP16 fields; assign digits to `source+residual`, decode them using the emitted FP16 fields in FP32 and set `residual=FP32(source+old_residual−decoded)`. K, recent BF16 V, Q, O and flush chronology are unchanged. Neither decoder nor cache stores the residual: it is separately billed producer state.

| Eight-head arm | Peak causal cache + residual | Final causal cache + residual |
| --- | ---: | ---: |
| Original K2/V2 G32/R32 | 304,768 B | 249,856 B |
| Frozen V feedback | 304,768 + 4,096 = **308,864 B** | 249,856 + 4,096 = **253,952 B** |
| Original-code V delay2 | **308,096 B** | **253,184 B** |
| Original K2/V4 | **361,856 B** | **307,200 B** |

These are per-sequence resident cache peaks *before* the t256 flush and final images *after* it, all eight KV heads. The common 2-B position counter, source residual, token IDs, source Q/K/V/teacher arrays, original checkpoint weights, timestamped event logs, prefix receipts and independent replay scratch are **not** secretly part of those cache savings. Common original layer-1 Q/K/V/O BF16 static weights alone are 12,582,912 B; three original layer-1 gain vectors add 2,560 B. The retained source NPZs total about 47 MiB compressed on disk (not inference-resident); the owned original capture/checkpoint are separate. Preparation pays input RMS, all Q/K/V projections, Q/K norm/RoPE, full teacher attention/O, and BF16 conversion. Per flushed feedback V vector there are 128 FP32 residual additions, 128 stored-field decodes, 128 FP32 subtractions, a 512-B residual write, original group extrema and 128 digit assignments. A straightforward producer has additional 512-B FP32 target and 512-B reconstructed vector and a 128-B code buffer per flush. `replay.py` temporarily expands K/V into up to `2×8×256×128×4 = 2,097,152 B` float32, plus full16-query scores/softmax, output and O weights. These are reader/preparation scratch and not priced as resident cache; there is **no native latency or speedup** measurement.

[`build.py`](build.py) writes actual per-head timestamped packed K/V event streams, t128/t256 preflush images, final cache images and **every** pre/post query cache SHA/byte/count and feedback residual SHA for all 256 positions. [`replay.py`](replay.py) parses the logs independently, verifies every event timestamp, source-based FP16 fields, original digits/K, feedback target/digit/recurrence, recent arrivals, prefix hashes and residual hashes, then independently decodes actual preflush packed caches for **every one of the 3,072 queries** and scores complete Q→softmax→V→original full O against the saved CPU teacher. Output SHA and double-precision SSE are per query in the 12 `*-result.json` receipts; [`aggregate.py`](aggregate.py) combines without retuning. A successful manifest is not substituted for the independent source/field replay. Torch and NumPy support code runs with one CPU thread, no GPU, full-model forward or recapture. All normal stages are sub-55-second per window:
