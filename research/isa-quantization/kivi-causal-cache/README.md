# KIVI asymmetric K/V: paid causal source control for Qwen's two-head GQA group

**Result.** A single predeclared KIVI 4-bit/G32/R32 control on the *original* Qwen3-0.6B layer-0 two-query-head/shared-K/V GQA group has **52,400 B peak causal cache state** and inspected-held GQA-pair post-O relative squared error **0.000155355**. At comparable counted state+table size, the frozen 49,664 B positive-feature prefix yields **1.53503**, and the previous 51,200 B per-token whole-vector affine Q6 cache yields **0.65695**. This is a strong named asymmetric-cache **CPU behavioral control on these windows**, not a full-model result, a current-SOTA claim, or a native timing result. The method/configuration was sent to the research coordinator before implementation and was not changed after seeing held losses.

## Primary method, source and scoped adaptations

KIVI is Liu et al., [*A Tuning-Free Asymmetric 2bit Quantization for KV Cache*, ICML 2024](https://proceedings.mlr.press/v235/liu24bz.html), [upstream implementation](https://github.com/jy-yuan/KIVI/tree/876b4d2d08e3b1d5f70d0969c299d8c7c42ddfb6) at `876b4d2d08e3b1d5f70d0969c299d8c7c42ddfb6` (MIT). Its [example.py](https://github.com/jy-yuan/KIVI/blob/876b4d2d08e3b1d5f70d0969c299d8c7c42ddfb6/example.py) explicitly sets group size 32 and residual length 32 with 2 bits; the upstream config/code supports **2 or 4 bits**. We fix **4 bits for both K and V**, group 32, residual 32, because it approaches the previously paid 50 KB comparator without a bit/group sweep. This is KIVI's supported 4-bit configuration, **not** the title's particular 2-bit result or a reproduction of the paper's model/task/throughput claims.

The [source implementation](https://github.com/jy-yuan/KIVI/blob/876b4d2d08e3b1d5f70d0969c299d8c7c42ddfb6/models/llama_kivi.py) groups **keys per channel over 32 successive tokens**, **values per token over four contiguous 32-coordinate groups**; each unsigned nibble group is assigned by min/max to 0…15 with scale `(max−min)/15`, an origin and step. Recent tokens are full precision; after computing the query for which the recent **K buffer reaches 32**, the 32-key slab is flushed, whereas the **oldest V** is flushed only when its recent buffer reaches **33**. Both rules are implemented literally by [`build.py`](build.py) and independently checked during the causal [`replay.py`](replay.py). There is no future-key calibration for earlier queries, no trained dictionary and no per-window quality selection. The group's two Q heads share **one** K cache and **one** V cache, as in the current upstream GQA path.

The distinct Qwen/CPU adaptation is explicit: Qwen's BF16-projected K is Qwen-K-normalized (BF16 internal rounding and original gamma), then position-RoPE rotated by the same FP32/Torch canonical source observer; **that rotary K is rounded to BF16 for the recent buffer and min/max quantizer input**. BF16-projected original V is also recent BF16. Source KIVI models commonly keep recent FP16; here BF16 matches Qwen's native storage width, although the original canonical teacher uses the **FP32 result of RoPE after its BF16 internal operations**. Quantizer origin and step are stored as **FP16**, calculated from available BF16 source values; codes use unrounded min/max/step with nearest-even assignment, then the independent reader uses stored FP16 fields. This is a named-method *CPU adaptation*, not bit-identical execution of upstream Triton/CUDA on Qwen. A separately priced recent-K-original-FP32 sensitivity arm isolates this boundary; it is not used to choose method or config. All original Q/K/V/O weights, two Q heads, norm gamma, RoPE, causal softmax and complete original O columns remain unchanged, with no source refit, GPU, new capture or model deployment.

The fixture is `/path/to/workspace/data/kelana-subbit/fixtures/qwen3-0.6b-wikitext/layer00-self_attn_q_proj.npz`, SHA256 `389e5f8c17ac151070b12094849f450130ab9c1684f51b402d59fd4e7ac2008f`. The original BF16 checkpoint revision `c1899de289a04d12100db370d81485cdf75e47ca` has SHA256 `f47f71177f32bcd101b7573ec9171e6a57f4f4d31148d38e382306f42996874b`; original Q head rows are checked elementwise identical to fixture. The same eight 256-token training windows and four inspected-held windows, original model parameters and CPU BF16 observer contract as [`../qwen-positive-kernel/`](../qwen-positive-kernel/) are used. The **1,573,376 B** two-Q/K/V/O/norm-gamma static group state is common unchanged state in all arms. Only the dynamic K/V cache differs. These are teacher-forced source windows, not continued generation or full-model perplexity.

## Chronological paid state, high-water and independent replay

At every insertion `t=1…256`, `build.py` appends just the currently available BF16 K/V. It serializes the **entire actual pre-query-flush cache** (quantized K chunks, quantized V tokens, recent K, recent V), hashes it, and only *after the query point* emits flush records for the newly complete K slab / newly aged V token and hashes the postflush state. Every original window has (a) a paid **46,592 B** final postflush image, (b) a timestamped chronological binary flush-event log of **39,096 B** (evidence, **not another retained inference cache**), (c) 256 before/after hashes and exact field counts in the manifest, and (d) byte snapshots before/after at positions 31, 32, 33, 255, 256. The event log contains eight 2,560-B key chunks and 224 80-B value tokens, with 3 B event type/position evidence per flush. Other packed fields in a prefix are never reconstructed from a *future* 256-token image during an earlier query.

`replay.py` imports **none** of the builder's quantization, packing or state-decoding functions. It reads each *actual emitted packed flush event* **only when that event's causal time arrives**; current recent K/V come from the source insertion at that time. It independently parses code nibbles, 128 K-channel or four V-coordinate FP16 origin/step pairs, and recent BF16 bytes, then does both original Q heads' full causal softmax/V/O. It verifies every prefix's exact byte length and SHA, all ten selected pre/post byte snapshots, the final paid image, and that every emitted code and field equals a separately computed min/max and nibble assignment using only source tokens available at that flush. It checks uncompressed online scores and O against the canonical all-window teacher: maximum differences **1.3352e−5 logits**, **7.302e−7 O coordinate**. The independent reader's 256-query errors are aggregated by actual absolute numerators and denominators, not the arithmetic mean of per-window relative errors. Individual source windows/images and hashes are in `*-manifest.json`, `*-final.bin`, `*-flush.bin`, `*-result.json`; [`results.json`](results.json) requires all twelve.

One key chunk is 2,048 B packed code +512 B FP16 fields (128 per-channel min/step pairs), a value token is 64 B nibble code +16 B FP16 fields (four per-token min/step pairs), and each BF16 recent vector is 256 B. At t32, K32 and V32 are used *uncompressed for that query*; K is then flushed, V remains uncompressed. At t33, the new key is recent and V33 remains recent for that query; only afterward does its oldest V become quantized. The 2-B current position count is shared with all readers and outside the displayed cache state (52,402 B including that common counter). There is **no** per-model static codebook/table or retained prepared magnitude matrix. The rank64 positive-feature competitor has 33,280 B dynamic moments +16,384 B shared feature table =49,664 B at length256; per-token affine Q6 is51,200 B, Q4 is34,816 B. The upper high-water exceeds feature+table by 2,736 B (5.5%) and Q6 by 1,200 B (2.34%); it is *not* equal-rate and not a proof of global dominance. The BF16 K/RoPE rounding control that instead keeps the original FP32 rotary K in the 32 recent slots costs **8,192 additional peak bytes** (60,592 B) and is not the primary image.

CPU replay materializes both decoded FP32 256×128 arrays per query at its largest prefix, adding **262,144 B transient scratch** at t256, plus score/output/teacher arrays used to measure the result; that scratch is **not** passed off as a 52,400 B complete CPU process. A fused/tiled KIVI reader can read packed codes/FP16 fields and recent vectors without a whole-cache FP32 expansion, but no gfx1151 lowering, emitted code census, register ledger, latency or full-model throughput is claimed here. Each K flush examines 32×128 available source scalars, min/max and 4-bit assignment; each V flush examines 128 available source scalars. At a query both heads consume the same K/V cache, do all visible causal score/value reductions, then original O; the complete work boundary includes producer K norm/RoPE, packing, unpack/dequant, recent-buffer mutation and flush, not just the moment state.

The **recent-K BF16 vs original-FP32** sensitivity changes held pair post-O only `.000155355 → .000154187`, so it does not explain KIVI's large advantage over these particular prior per-token K controls. Per-channel K isolates persistent outlier channels across token positions; the prior controls used one 128-vector scale per token, a much weaker key rate allocation. This is not evidence KIVI beats a strong rotated/outlier-aware cache, source-preserving gamma gauge, optimized scalar quantizer, or *all* compact positive kernels. In particular, the independent source-preserving Q/K paired-power-of-two gauge was not tested or used to choose this primary. The source method's original 2-bit configuration and any tuned residual length remain unmeasured. Unlike the positive-kernel prefix, this cache still grows with context length; no asymptotic replacement is asserted.

Run `build.py PANEL WINDOW` and then `replay.py PANEL WINDOW`, with PANEL=`train`, WINDOW0…7 and PANEL=`held`, WINDOW0…3; `aggregate.py` requires the complete set. Use `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /path/to/workspace/data/fish-s2-pro/venv/bin/python`, each individual build and replay under a minute. `source.py` vectorizes original source projections across the window for CPU efficiency but **only the current token's** bytes enter the online cache and group quantization is delayed to its causal flush. The observed paid images and chronological event logs, not the vectorized preparation arrays, are what the independent reader consumes. No CUDA/Triton backend, GPU job admission, new compute, new capture or service deployment is involved. The parent owns shared machine/research catalogue documentation.
