# Later named KV comparators: source-boundary selection

**Decision (source audit only; no candidate built or scored).** Of the three inspected routes, **paper-specified TurboQuant** is the cleanest *next independent layer-0 causal cache comparator*, conditional on implementing its actual random rotation, MSE code and (for key scores) separate QJL residual/inner-product consumer. Its authors' public paper describes an online, data-oblivious encoder, so the existing 256-token Qwen3-0.6B layer-0 capture can supply every arrived K/V and current Q without future-token or other-layer information. There is **no located official public implementation or pinned official code commit**: this recommendation is a source-defined port, not a claim of reproducing an official kernel, established quality, current SOTA, comparable rate, or speed. Community repositories are not substitutes for author source. RotateKV's rotation is a valid alternative in principle but its available official simulation selects protected tokens using a whole-sequence pivot calculation; AQUA-KV's defining predictor needs other layers and calibration not present in this capture. Neither negative statement rules out a separately scoped faithful full-model implementation.

## Fixed source and boundary

The original two-query-head group has **one** shared 128D K/V head; the complete layer has **16 Q and eight 128D K/V heads**, each 256-token window. The frozen Qwen3-0.6B checkpoint revision is `c1899de289a04d12100db370d81485cdf75e47ca`, checkpoint SHA256 `f47f71177f32bcd101b7573ec9171e6a57f4f4d31148d38e382306f42996874b`; captured layer-0 input fixture SHA256 `389e5f8c17ac151070b12094849f450130ab9c1684f51b402d59fd4e7ac2008f`. See [the existing causal KIVI reader](../kivi-causal-cache/README.md) and [full-layer SKVQ](../skvq-global-gqa/README.md). The teacher's Q/K RMSNorm, BF16 boundaries, RoPE, all Q heads, shared K/V, causal softmax and full O must stay paid and unchanged. Earlier queries cannot see final-image keys. This is one observed layer, not full-model perplexity or long-context generation.

## Paper rate arithmetic and chosen source placement

The ICLR2026 paper's LongBench discussion and arXivv1 give32 outlier channels at3 bits plus96 channels at2 bits as an example of “2.5-bit” precision. The stated code allocation is actually **(32×3+96×2)/128=2.25 bits** before any fields; extra norms or a different allocation are not specified by that sentence. Preserve this published discrepancy rather than copy the label into a byte ledger. The base Algorithms1/2 remain explicit enough for a uniform algorithm port, but it is not a reproduction of that mixed-channel evaluation.

The selected subsequent implementation uses the same **post-RoPE BF16 K insertion boundary as the frozen KIVI control**, with original FP32 source scores as teacher. It does not inherit SKVQ's pre-RoPE cache. Then one transformed query can serve all cached keys in the asymmetric MSE+QJL score map. A pre-RoPE placement would require position-dependent transformed queries or reconstructed/rotated keys, changing executable work substantially. Source placement was fixed before any candidate encoding or output.

## Honest illustrative TurboQuant byte/work ledger, not an image

For the fixed **K3+V2** illustration, per KV head/token: K has 128×(2 index bits +1 QJL sign)=48 B, V has 128×2 bits=32 B, hence **80 B codes/token**, **20,480 B/head** at256 and **163,840 B/eight-head layer**. Paying **three serialized FP32 scalars per head/token**—K original radius, K residual norm, V original radius—adds **3,072 B/head**, giving **23,552 B/head** and **188,416 B/layer** before shared assets, current position and alignment. FP32 is a *proposed finite-storage adaptation*: the paper's mathematical sphere/radius and Gaussian transform are real-valued and do not imply exactness after FP32 normalization, rotation or stored fields. The radius count presumes a separately scaled original K and V; no residual field is charged for value MSE. The existing original group KIVI peak is 52,400 B, complete layer KIVI peak 419,200 B; comparing code bits alone with either is invalid, and this low-rate illustration is not a same-rate quality claim.

A reproducible seed for each random object, two rotated-sphere codebooks, generation and preparation of **K/V 128×128 orthogonal transforms plus a 128×128 QJL Gaussian map** and their finite storage must be paid. For an illustrative three distinct FP32 prepared dense matrices, that is **196,608 B shared across heads** (or a specified smaller algebraically justified shared transform and its preparation; do not silently zero it). An exact paper Haar matrix requires QR preparation, not an unpriced 128-point Hadamard substitution. Each newly arrived key needs norm/rotation, MSE indexing, inverse approximation, residual, dense QJL projection/sign/norm; each V needs norm/rotation/index. At each causal query, both query heads consume the same packed K, including the **QJL score correction**, all earlier V, softmax and original O; quantizer lookup, matrix reads, query transforms, normalization and scratch must be charged. Efficient fusion or performance is **unmeasured**. If a future executable implementation cannot retain the paper's dense projection within acceptable shared model asset/work budget, that is a cost obstruction, not permission to label a different sketch TurboQuant.

**Selection rationale:** TurboQuant can be defined with *only current token* inputs and immutable shared randomness; it changes key-score representation, unlike the already tested KIVI/SKVQ grid/retention policy. Its official-code absence and dense random maps are material liabilities. RotateKV would be the alternate if the task permits a newly specified causal pivot adaptation and train calibration; AQUA-KV first needs a new cross-layer capture/calibration task. This report makes no fit, timing, win, author-affiliation claim for community code, or post-2026 SOTA ranking.
