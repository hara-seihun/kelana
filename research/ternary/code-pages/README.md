# Exact page-addressed trit codes for the complete 0.6B image

The frozen `fresh-duration32` Qwen3-0.6B image has 119,196,989 radix-243 code bytes across 197 matrices. Its existing exact 256-row FP16 scale-page image costs **125,953,725 bytes / 1.690512432 BPW**. A per-matrix directory of 32-bit offsets and independent **16,384-code-byte pages**, zlib level 1 where shorter (one flag byte per page), saves **2,977,841 physical bytes**. The saved complete image is **122,975,884 bytes / 1.650544760 BPW** for 596,049,920 unique parameters. All 7,360 saved pages decode exactly to the original code bytes; shape, Hadamard signs, BF16 norms and the already-paid FP16 scale pages are byte-identical. The previous held complete-model loss **4.498337 NLL over 2,040 disjoint predictions** therefore applies to this same decoded image, not to a newly trained numerical model. Source/scale-image/197 input and 197 output hashes, directory/page counts and physical sizes are in [the complete receipt](/path/to/workspace/data/kelana-subbit/ternary/fresh-duration32-code-page-16384/receipt.json).

[The complete-code entropy accounting](ENTROPY.md) checks all 119,196,989 original code bytes: even an oracle per-matrix static IID arithmetic coder with free models saves at most another **766,263 bytes / .010285 complete BPW** below the paid zlib pages. A per-matrix first-order model has at most 1.904 MB of apparent transition-bit headroom before first symbols and its up-to-59,049 probabilities per matrix are paid. This is a restricted static-context rate bound, not an unconditional compression limit or a direct consumer.

[The native complete-image consumer panel](NATIVE.md) removes Python from the timed loop: all 7,360 pages verify byte-for-byte, and eight paired C++/zlib passes cost **303.819 vs 15.457 ms** for all code bytes, or **293.488 vs 0.285 ms** for one shuffled code per page. The full-stream CRC matches [the prior Python/zlib panel](CONSUMER.md), which measured 315.33 vs 22.76 ms; interpreter overhead did not explain the cold inflation cost. This is a host-CPU boundary negative, not native GPU inference. Decode once into a hot image until a direct compressed-label consumer is constructed and measured.

Independent page access has a cost. To read one previously cold code, first read its 4-byte directory entry and a compressed page, inflate up to 16 KiB of trit codes into scratch, then use the existing radix-243 decoder. This is **not** a direct packed consumer, a GPU rate or a serving image. If every page is visited exactly once in a streaming whole-model pass, at least the 116,219,148 paid code bytes must be read *plus* 119,196,989 decoded bytes written/read at the conversion boundary; extra decompression and scratch cannot be counted free. A cold random code access can require an entire page read and inflation. Without a native fused, page-local decoder that pays less than the saved weight traffic, the selected direct radix-243 format remains faster by no demonstrated amount. The next useful question is a cheap direct-consumption coordinate with **small independently decoded tiles**, rather than treating storage compression as a speedup.

An exact full-matrix page sweep with the same zlib-1-or-raw grammar (no saved alternative images) finds 4 KiB pages cost **124,482,370 bytes / 1.670764355 BPW** and 64 KiB pages cost **122,874,631 bytes / 1.649185773 BPW**. The latter saves another 101,253 bytes but quadruples the worst cold-page expansion; 16 KiB is the reported addressability point, not a universal optimum. All sizes include page flags, directory offsets (including the end), code bytes, scales, signs, shape and norms; no `npz` wrapper bytes are counted. This exact physical-rate result neither closes the large 0.6B loss gap to BF16 nor transfers to Qwen3.6 MoE without a trained whole-model image.

Reproduce on CPU: `python3 research/ternary/code-pages/measure.py --image fresh-duration32 --scale-image fresh-duration32-page-256 --output NEW-NAME --page-bytes 16384`. Each saved file is reopened and independently decoded against all original code bytes, while all other payload bytes are checked against the already-paid image. The experiment requires no GPU reservation and does not change the running Bonsai service.
