# Token-keyed Q/K work stops before RoPE

The [value append study](../value-token-id-cache/README.md) found that the first layer's BF16 QKV input is a function of token ID on twelve separate Qwen3-0.6B windows. This study asks whether the same exact input fiber can skip the *paid binary Q/K projection*, without incorrectly caching a position-dependent rotated key. It can. The useful cache boundary is after Q/K projection and head RMSNorm, before RoPE.

Let `x(i)` be the layer-0 QKV input for token ID `i`. For fixed paid Q/K image and normalization `N`, define `q(i)=N_Q(P_Q(x(i)))` and `k(i)=N_K(P_K(x(i)))` with the actual BF16 conversion points. The attention score at positions `s,t` still uses `R_s q(i_s)` and `R_t k(i_t)`. If the same ID has bitwise equal `x` and the projection is deterministic, reusing `q(i),k(i)` on a hit gives exactly the previous pre-RoPE bits. Apply RoPE at the **current** position and keep the usual positional K cache and causal attention. This is a schedule, not a new quantizer or a change in quality. A lookup keyed by `(ID, layer-0 image identity)` is valid only within a model/image lifetime; a block-local first-seen table needs neither eviction nor an assumption about other layers.

The pre-RoPE cache need not hold all 3,072 BF16 Q/K outputs if the observer uses the frozen [paid 112-plane mask](../paid-qk-plane-allocation/README.md). For each group, retain the selected two Q heads and one K head, both coordinates of each selected RoPE plane. That is `2 * 3 * 112 = 672` BF16 scalars or **1,344 bytes per new token ID**, rather than 6,144 bytes for full Q/K. RoPE preserves each plane, so selected coordinates suffice for that selected-score consumer. It still needs the full raw K projection on a miss for the norm denominator; narrowing the memo does not make the producer a selected-row K projection. The group-specific key affine can likewise be applied before memoization if its paid BF16 rounding is retained. This selected cache is transient producer state, not stored model BPW or a replacement for the position-dependent key cache.

On four *separate* original-producer validation windows, first-seen token counts are 147, 148, 127, 146 of 256. All **456** repeated inputs reproduce every pre-RoPE Q/K BF16 bit from the actual paid images. A CPU replay projects and normalizes all 1,024 rows as a control, projects only first-seen rows for the memo, then checks the BF16 output, FP32 position-rotated Q/K and all selected-plane coordinates. Conversely, naively copying a first occurrence's rotated vector at its new position disagrees on **all 456 hits for both Q and K**. Source, model, capture, token, image and mask hashes, plus per-window output hashes, are in the [receipt](/path/to/workspace/data/kelana-subbit/qk-token-orbit/receipt.json).

That is 44.53% of logical Q/K factor terms on these windows. The full-Q/K memo occupies 3,489,792 BF16 bytes summed over four separate 256-token windows; the selected-plane memo occupies 763,392. Hits read 2,801,664 or 612,864 BF16 bytes respectively, excluding table probes and writes. The same hits offer another 104,595,456 narrow-V right-factor terms via the prior V memo, so one shared first-layer ID table can gate both independent projections. Do not add these unlike terms as a GPU time estimate.

The replay expands the paid binary factors to BF16 exactly as the existing causal quality experiment does. Its term counts describe a direct binary-factor producer; this is **not** a native timing or proof that an expanded BF16 matmul is a cheap consumer. The memo adds first-seen projection writes, token lookup, table state, per-hit coordinate reads and positional rotation. Q/K normalize only on misses; the key cache is still appended per occurrence and score/O/head work is unchanged. A device implementation should first compare complete layer-0 Q/K/V append plus attention at occupied context against the current paid direct consumers, with the shared ID lookup, selected-plane table, RoPE, norm and cache append inside timing. If those loads and table probes eat the projection gain, train an inexpensive token-conditioned paid response table or a codebook shared with the projection rather than extending this memo to later layers. At layer 14 the same IDs do *not* preserve the QKV input, so token-only reuse there is invalid.
