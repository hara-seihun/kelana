# Token IDs eliminate repeated layer-0 value projections

The exact signed-byte narrow-V dictionary currently discovers repeats *after* projecting 1,024 BF16 input coordinates through eight paid 28-row right factors and quantizing 224 values. On Qwen3-0.6B layer 0, the token ID itself is a sufficient dictionary key. The model starts from a token embedding; its first Q/K/V input has no prior position-dependent transformation. RoPE acts on Q and K after their projections, not on this shared input. The paid V code is a deterministic function of that input. An appender can look up the token ID, reuse its earlier 224-byte code and emit the earlier byte label without running V's right-factor projection or its code quantizer again.

The observation is exact for this layer and this model, not a weight-quantization quality gain. For a stream block, let `x_t` be the actual BF16 input to `v_proj`, `i_t` the token ID, and `C(x_t)` the paid 224-byte code. If `i_s=i_t` implies bitwise `x_s=x_t`, then determinism gives `C(x_s)=C(x_t)`; assigning both the same byte label gives the original value cache and the same subsequent attention/O map. First-seen token labels equal first-seen input labels when the converse also holds. A table storing `token_id -> byte_label`, scoped to the dictionary block, needs no 224-byte comparison on a hit. A miss still computes and stores the paid code. This does not skip K, Q, attention, the O decoder or output-head rows.

The capture has raw BF16 bit patterns of the actual `self_attn.q_proj` input, which is also the V input. The pinned token fixture is the one used by the capture program. The script compares every first-seen label, not only the number of distinct rows. Four original-producer 256-token validation windows already have parent receipts showing that each of the eight paid 28-byte V code groups has the same distinct-prefix labels as these input rows. Thus the value-cache bytes and integer consumer remain the parent's measured map. The extra eight training windows test the input identity, without claiming a new code-quality panel.

Each window resets the dictionary. Layer 0's 1,326 hits in 3,072 positions bypass 43.16% of the V right-factor term count, 304,152,576 of 704,643,072. The four validation windows have 147, 148, 127 and 146 distinct token IDs, exactly the parent's 147, 148, 127 and 146 distinct input/code labels. The existing exact cache charges 125.273 bytes/key on those windows, against 224 for raw rows. The new token lookup is *additional metadata*, not free: an eight-byte entry per distinct token would add 4.438 bytes/key on validation if stored in the same device budget. A compact open-addressed lookup also needs empty slots and probes; a direct vocabulary table needs an epoch or clearing strategy. CPU-host lookup, GPU hash work, the paid projection's actual hardware cost, block restarts, the input's BF16 normalization and output-side work have not been timed. The term reduction is not a latency claim.

At layer 14 the same token IDs repeat 1,326 times but **every repeated ID has a different producer input**. The naive token-keyed memo is invalid there, even though its token-frequency estimate would predict exactly the same work reduction as layer 0. The upstream state, not the token ID, owns later-layer value identity. Do not spread the layer-0 specialization across the transformer.

The next useful native experiment is a fused layer-0 append that tests the ID before constructing the paid V code, using the current indexed signed-byte reader against the same image with the code-based append. Time projection, lookup, quantization, scatter, count reduction and O together at occupied context; a hit might not help if another projection or scheduling dominates. For stronger compression, learn a V producer with repeat-rich codes across *different* inputs, rather than mistaking layer-0 embedding reuse for a quantizer quotient. No GPU, whole-model NLL, installed executable or service state changed in this study.
