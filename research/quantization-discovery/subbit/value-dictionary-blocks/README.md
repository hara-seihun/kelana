# Where should a repeated narrow-value label dictionary reset?

The paid signed-byte rank-28 V cache at Qwen3-0.6B layer 0 repeats complete 224-byte rows. The preceding [256-key dictionary](../value-label-histogram/README.md) charges 125.273 bytes/key and its [grouped sparse-overflow consumer](../value-label-overflow/README.md) pays a dot over distinct labels in each causal prefix. A dictionary need not reset every 256 *keys*: one byte can name 256 *distinct rows*. Resetting only when the next new row arrives is an append-only construction. On a concatenation of four previously inspected 256-token capture windows it cuts charged bytes 128,280 to 122,450, with no second byte per ID, and lowers logical causal label uses 301,855 to 286,978 per group. A 1,024-key two-byte-ID block charges 107,782 bytes, 105.256 bytes/key, and 265,140 label uses. These longer-cache numbers are a **storage and integer-program stress test on concatenated separate texts**, not a real 1,024-token Qwen continuation. The actual 256-token windows only support the within-window causal comparison below.

A block is an ordered list of distinct whole V rows, a byte ID for each key, a uint16 label count and a uint32 arena address. The appender copies a row and assigns the next ID only when its 224-byte value is new. Before the 257th new row it closes the block and starts a new one. Completed blocks never move. The index is shared by eight GQA groups because a whole-row identity implies the identity of every 28-byte group code. The reverse does not follow: when the four windows are concatenated, layer 14 group-specific collisions do not coincide with whole-row collisions. A group-specific dictionary's smaller label count cannot be used with a shared ID unless its actual equivalence classes are checked. The source checks first-occurrence IDs for every group within each real window and checks the integer dot using whole-row IDs on every group of the concatenation.

For any nonnegative causal integer masses `n[h,k]` and any partition into completed blocks plus the current prefix, accumulate `H[h,b,j] = sum_{k in block b, id(k)=j} n[h,k]`. Then `sum_k n[h,k] c[k] = sum_{b,j} H[h,b,j] c[b,j]` in integer arithmetic. With a conserved 4,095-unit mass and signed-byte coordinates in `[-127,127]`, both sides fit int32 because their absolute value is at most 520,065. The 15-overflow-label bound of the grouped sparse reader applies **globally** across all blocks, not fifteen per block, since each overflowing label consumes at least 256 mass units. Splitting the histogram at a block boundary changes neither that bound nor the real-valued scaling stage. It does change dot work: each previous block's labels need revisiting on later queries, so the code counts all completed blocks, not merely the current block's prefix. FP32 reassociation is not covered by the integer identity.

## Measured fixed-cache costs

Four separate 256-token original-producer validation windows, eight groups, paid rank-28 signed-byte codes. Values aggregate across all four windows; all byte rates include 224 bytes per unique whole row, one ID per key and six bytes per block. One group has `4 × 32,896 = 131,584` direct causal key uses. The grouped reader uses two heads and 28 coordinates, so multiply the label-use count by 56 for logical code products. Every query still scatters its causal key masses into the histogram; fewer products do not eliminate scatter or zeroing.

The first four rows' costs are computed separately for each window and summed; a query never crosses a window. The `measure.py` receipt retains every window and group, including hash-checked integer response. Do not interpret a short block's *local prefix* sum as its total dot work: completed blocks remain live to later causal queries. Layer 14 has 1,024 distinct whole rows, so its indexed reader costs 225.023 bytes/key against 224 raw and saves no dot products. It should bypass the dictionary.

For **storage-only** concatenation of the four separate windows, the layer-0 256-key baseline costs 128,280 bytes (125.273 bytes/key). Byte-ID adaptive blocks of lengths 472, 515 and 37 cost 122,450 (119.580 bytes/key); the two-byte-ID 512- and 1,024-key blocks cost 117,868 and 107,782 (115.105 and 105.256 bytes/key). The corresponding synthetic causal label-use counts are 301,855, 286,978, 281,410 and 265,140, versus 524,800 direct key uses. Layer 14 costs 230,424 bytes at 256/adaptive and 231,430 at 1,024; it gains nothing on synthetic dot work. A wider 1,024 block beats the frozen 112-byte nibble cache **on bytes in this constructed stream**, but has different signed-byte values, a dictionary lookup at append, two-byte IDs, histogram work and an unpaid native reader. This is neither a quality-matched quantizer win nor an inference-speed result.

The actual within-window result is less exciting but clarifies the design: a 256-key block is preferable to 32/64/128 on both stored bytes and counted causal label products. There is no reason to reset a layer-0 dictionary at a smaller fixed width for this frozen image. Larger blocks are promising only if the 1024-context producer actually repeats whole rows; measure a real occupied context and price append/index/count/scatter/dot/correction/O under the native wrapper before changing a cache. For layer 14 bypass the index. No GPU, executable, service, whole-model NLL or native timing changed.
