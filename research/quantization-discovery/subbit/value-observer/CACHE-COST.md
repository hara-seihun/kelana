# A line-aligned narrow-value consumer

The paid rank-28 image has eight shared GQA groups, two query heads per group and 28 BF16 value coordinates per group. The previous 448-byte/token cache estimate is a storage count, not necessarily the cheapest address coordinate for a native attention kernel. This note settles the 64-byte-line layout choice for a consumer that loads one group's value per key and query head. It also gives a concrete fused schedule. This is a transaction model and an executable design, not measured gfx1151 latency.

## The two cache coordinates

For each token, put K in its existing 2,048-byte region. The compact V region has eight adjacent 56-byte group segments, 448 bytes total. If the first group starts on a 64-byte line, its group start offsets modulo 64 are `0,56,48,40,32,24,16,8`. Groups 0 and 7 fit within one line; the other six straddle two. Thus a group-by-group load asks for **14 line segments per key** and two separately scheduled query heads ask for **28**, though the union contains only seven distinct lines. Counting 28 as DRAM transactions would be wrong when those lines hit cache or combine across groups.

Instead store each group in one aligned 64-byte slot, with its last four BF16 coordinates zero. V becomes 512 bytes/token, eight lines. Now there are **eight line segments per key** for one scheduled query head, or 16 for two independent heads. Relative to the compact form, the padded form spends one more distinct line and 64 more bytes per token, but removes 12 of 28 per-head line requests. Both representations carry exactly the same 28 meaningful coordinates. The aligned layout avoids an unaligned two-line group load and gives the consumer a fixed 64-byte stride; it does not charge four extra arithmetic coordinates if the consumer masks its last four lanes.

These two points are Pareto-optimal in this restricted layout grammar. Eight disjoint 56-byte group segments occupy 448 bytes. Seven contiguous 64-byte lines hold exactly 448 bytes, so a seven-line layout has no room for a gap and has the compact crossing pattern above, up to permutation of the groups. To keep every segment within one line, each of the eight groups needs its own line: two 56-byte groups cannot fit together. The minimum is eight lines, achieved by the padded coordinate. Moving or duplicating bytes and fusing heads are different grammars; this is **not** a universal memory-traffic lower bound.

One work unit can own both query heads of a GQA group for the same key range. It loads one 56-byte vector and the two distinct attention coefficients, then updates two 28-coordinate accumulators. Each head still visits keys in increasing order with its own FP32 FMA chain; the group shares the value fetch, not the attention probability. This halves the modeled value line requests to 14 compact or eight aligned per `(group set, key)` without reconstructing any 128-wide value. It adds live accumulators and may cut occupancy, so both the unfused and fused schedules must be timed. BF16 casts, softmax order and final decoder rounding need explicit matching to the chosen quantized-map reference; the algebra alone does not promise bitwise equality with the original model.

## What the bytes buy

For Qwen3-0.6B's 28 layers, eight KV groups, sixteen query heads, BF16 K/V and a 4,096-token occupied prefix, the original K/V cache is 448 MiB. Rank-28 compact is 273 MiB and rank-28 aligned is 280 MiB. The aligned form still saves **168 MiB** of resident cache against original V, instead of 175 MiB for compact. The corresponding headwise V payload read across all keys and layers is 448 MiB original, 98 MiB compact and 112 MiB aligned, assuming each query head reads its group's value independently. Thus aligned saves 336 MiB of requested value bytes per generated token. With a perfect two-head shared load the absolute figures halve, and the benefit over an equally fused original-V consumer halves too. These are requested bytes, not necessarily off-chip bytes, especially at short context.

At the 242 GB/s streaming rate measured for Bonsai's different 27B engine, 336 MiB would take 1.456 ms. This converts the *byte saving* to a scale for an experiment; it is neither a latency lower bound nor a predicted Qwen3 speedup. Narrow decoding adds signed-grid factor work, scales, output reductions and preparation. Those operations can cost more than the value-cache saving, particularly when the original V remains in cache. The earlier [value observer](README.md) counts 688,128 signed-grid terms versus 1,605,632 binary terms per token, but their instruction and launch costs are not interchangeable. Stored factor bytes remain 208,640 per V/O pair at rank 28; cache padding changes runtime KV bytes, not weight rate.

`cache_cost.py` prints exact 64-byte-line requests, stored KV and requested value bytes for ranks 24, 28 and 32. For the current paid rank-24 images, compact V is 48 bytes per group: four groups straddle a line and four fit, or 24 line requests in total over two independently scheduled heads, versus 16 with 64-byte slots. Rank 32 naturally fits one slot per group. The rank-24 image saves another 7 MiB of KV cache over rank-28 compact at a 4,096-token prefix, but its [fresh loss](FRESH-LOSS.md) prevents choosing it on bytes alone.

## Decisive native experiment

Build one attention-only panel on the **same frozen rank-28 V/O image**, original Q/K and identical occupied prefixes at 256, 4,096 and 16,384 keys. Compare compact and aligned cache layout with one-head and paired-head consumption, report cache-line request counters where available, VGPR/occupancy and full value-read plus O-consumer time. Keep preparation, K reads, attention probabilities, output reduction and all casts inside the timed region. Compare against an independent binary V/O consumer at its actual rate, not BF16-expanded weights. If aligned wins but pairing loses occupancy, keep aligned and schedule heads separately; if compact wins through line sharing, spend no cache bytes on alignment. Neither cache coordinate warrants serving integration before fresh composed-model quality improves.
