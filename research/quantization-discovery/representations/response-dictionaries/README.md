# Shared response dictionaries on a real ternary block

The real 5,120 by 128 Bonsai down-projection block does not have enough repeated eight-weight shapes to make a small learned dictionary a useful default. A 16-entry dictionary uses 55,296 bytes, but loses 0.754 relative RMS on held output rows and eight captured inputs. A larger 64-entry dictionary uses 88,064 bytes and still loses 0.611. A scalar sign code whose fitted gain is folded into the source FP16 scale uses 92,160 bytes and loses 0.529; the original exact base-three image uses 143,360 bytes. These are different points on a poor quality/rate frontier, not a whole-model judgment.

## Encoded object and consumer

Split every row into sixteen eight-trit pieces. For each of the sixteen *column positions*, fit `K` shared eight-dimensional centroids to the first 4,096 output rows by unweighted Euclidean K-means. Round the centroids to FP16, then reassign all 5,120 rows against those stored centroids. The final 1,024 rows and all eight captured signed-int8 inputs are held out from fitting. The original FP16 source scale remains attached to each row. No input-side or output-side correction is fitted.

For a fresh input `x`, prepare `T[j,c] = sum_a float16(D[j,c,a])*x[8j+a]`, then compute `y[r] = scale[r]*sum_j T[j,id[r,j]]`. The original weights never appear in this online map. The native program reads the bit-packed IDs, converts each FP16 dictionary entry while preparing its table, gathers sixteen FP32 responses per row, accumulates, then applies the FP16 row scale. That preparation costs `16*K*8` coefficient-input products per input, followed by 81,920 ID extractions, table accesses and additions and 5,120 scale applications. The table itself occupies `16*K*4` transient FP32 bytes. This is response reuse across rows, not the existing sign-orbit lookup for every possible ternary chunk.

`results.json` charges all physically stored model bytes: `5,120*16*log2(K)/8` packed ID bytes, `16*K*8*2` FP16 dictionary bytes and 10,240 original FP16 scale bytes. The native program allocates output and the prepared table in addition. There is no separately stored selector, exception or learned transform. The format's dimensions are fixed by the fixture; standalone container metadata is excluded for *all* arms.

The one-spike control has the same four-bit ID payload as `K=16` but no learned dictionary. It selects one actual signed trit per eight inputs. The stronger scalar sign control pays 81,920 sign-code bytes and 10,240 bytes for the combined FP16 row scale. Its gain minimizes isotropic squared weight error, not held response error. We multiply each source FP16 scale by that fitted gain offline and round the product once to FP16. This produces 0.52873129 held RMS, versus 0.52873111 if we retain both scales separately at 102,400 bytes. None of the 5,120 folded scales is zero or nonfinite. The two-scale image is unnecessary for this single consumer; only a separate consumer that needs the original scale could justify retaining both. Exact HALO bytes use 26 base-three bytes and two FP16 scale bytes per row. The native exact figure is the existing [single-core packed SIMD panel](../../SIMD.md), **not** a paired measurement against this C++ kernel. The dictionary timing is a scalar native lowering over 31 passes per captured query, including fresh preparation, packed-ID extraction and all row outputs. The output agrees with the independent NumPy expression within 0.000016 absolute. The `K=16` median was 54.688 µs on the preceding run and 37.029 µs on the folded-scale rerun, so this unpinned panel cannot support a fine-grained speed comparison. Timings exclude disk reads and full-model inference; an optimized SIMD table lookup could improve this lowering.

The held score is RMS of the scaled output error divided by RMS of the exact scaled output on the same 1,024 rows and eight inputs. It is not weight SSE or language loss. Across all 5,120 rows the `K=16` score is 0.73595; holding rows out matters. Per-position learned dictionaries are deliberately generous to the candidate, rather than demanding a single shared dictionary across the entire matrix.

## Is the reusable shape there?

At a fixed eight-column position, the block has 3,550 distinct eight-trit vectors among 5,120 rows on average. The sixteen most frequent exact vectors cover only 1.423% of rows. An independent-trit source drawn from the block's empirical marginal gives 3,544.6 distinct vectors and 1.417% top-sixteen coverage. On this control, the same trained `K=16` codec scores 0.75758 held RMS versus 0.75436 on real rows. The real block has no substantial visible eight-trit motif advantage under this test. Four-trit positions already realize all 81 possible vectors; sixteen-trit positions have essentially one distinct vector per row. This is a negative for **these independently fitted local response dictionaries**, not for dictionaries shared across layers, correlated expert routes, producer-conditioned states or downstream compositions.

A native exact response lookup already exploits the useful short ternary symmetry. It packs three-trit sign orbits into five-bit codes and prepares 43 small tables per fresh input. Our longer learned vectors require fewer gathers but exchange exactness for quality loss and a larger prepared table. The direct CPU result and its GPU reversal are documented in [the owning discovery report](../../README.md); this experiment does not claim that unrelated host timings establish a universal speed ordering.

The cheapest transfer test is one routed expert or one complete Qwen FFN layer with held activations: fit dictionaries on disjoint rows or experts, run the actual nonlinear consumer and compare held logits or loss against a paid scalar PTQ image. If shared motifs do not improve the held response beyond this independent-trit control, stop before writing a GPU gather kernel. If they do, charge expert-specific IDs, reusable tables, runtime preparation and cache traffic in a paired native run.
