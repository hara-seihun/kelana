# When a one-byte direction/radius code earns its lookup

I tested a fixed polar code against scaled scalar codes on real BF16 gate/up weights from Qwen3-0.6B layer 0. One pair is `(gate[row,k], up[row,k])`. Rows 0–7 set shared FP16 gains; rows 8–15, columns 0–1023 provide 8,192 held pairs. Each held pair gets its best index under the declared consumer metric. This is a weight-reconstruction experiment with a small *linear* consumer, not a SwiGLU or language-quality measurement.

For each row, the online map is `y += C * w_hat[:,k] * x[k]`, summed over `k`. The isotropic case has `C=I`. The anisotropic case uses `C=diag(1,0.05) S`, where `S=[[1,1],[1,-1]]/sqrt(2)`. Its expected squared output error under independent, unit-variance inputs is `sum_k (w-w_hat)^T C^T C (w-w_hat)`. The table gives that error **per pair**, with no accidental cancellation between columns. The inputs are a declared evaluation distribution, not captured transformer activations. Both encoders assign codes by the same metric. In particular, the scalar control is *not* selected by Euclidean nearest-weight rounding when the consumer is anisotropic.

The polar byte has five angle bits and three radius bits. Its 32 equally spaced directions and eight radius factors `[.22,.46,.72,1.04,1.46,2.02,2.80,4.0]` are fixed in source. One FP16 RMS gain, learned only from the first eight rows, multiplies the radius. There is no per-pair scale and no learned vector dictionary. A pair reads a byte, selects two already-scaled FP16 weights from a 1,024-byte table prepared once for the layer, and performs two activation products and two row additions. The table is generated from fixed constants and the paid gain, rather than stored with the model. Building and accessing it are real costs, not claimed free. One could generate sine/cosine and the radius on every consumption instead, but that exchanges table traffic for more arithmetic.

The equal-byte scalar control has two quaternary scalar labels `{-3,-1,1,3}` in four bits and one of 16 fixed geometric scale factors in four bits. It also pays one shared FP16 RMS gain. A stronger version trains all 16 FP16 scale values on rows 0–7 with 16 alternating assignment/least-squares steps, freezes them, and charges 32 model-dependent bytes instead of two gain bytes. This is a local fit, not a global codebook optimum. Both versions use a 32-byte scale lookup, followed by two label multiplies and the consumer. A 16-by-16 fixed Cartesian grid and several directly consumed sum/difference codes are additional one-byte controls. The rotated variants use separate FP16 RMS gains for sum and difference. The sum-only variant uses just one. These direct codes select pre-scaled sum/difference operands and feed the anisotropic consumer without reconstructing gate/up weights; their lookup sizes are in the receipt. The `6+2` and `7+1` tail variants allocate more labels to the sum and reserve several fixed labels for heavy tails. No per-pair escape or learned correction is allowed.

Two stronger scalar controls enumerate all nine ternary or sixteen quaternary vector patterns. Each pattern gets its optimal nonnegative pair scale in the consumer metric, rounded to its best neighboring FP16 value. A byte stores the pattern index and two bytes store the scale, **three bytes per pair**. The zero ternary pattern has zero scale. These controls need more bytes but they show what continuous scale freedom buys.

| Method | Weight bytes for 8,192 pairs, plus shared gain | Isotropic error | Sum-dominant error |
| --- | ---: | ---: | ---: |
| Polar 32×8 | 8,192 + 2 | 4.23677e-5 | 2.32938e-6 |
| Cartesian 16×16 | 8,192 + 2 | 1.40674e-4 | 8.67752e-6 |
| Scalar quaternary × 16 fixed scales | 8,192 + 2 | 7.21437e-5 | 2.25049e-6 |
| Scalar quaternary × 16 fitted scales | 8,192 + 32 | 6.95320e-5 | **2.09838e-6** |
| Direct rotated 6+2 with tails | 8,192 + 4 | 2.25499e-4 | 4.98181e-6 |
| Direct rotated 7+1 with tails | 8,192 + 4 | 5.00567e-4 | 2.77959e-6 |
| Scalar ternary × FP16 scale | 24,576 | 1.05934e-4 | 8.94815e-7 |
| Scalar quaternary × FP16 scale | 24,576 | 5.80832e-5 | **5.73551e-7** |

The polar code wins the isotropic one-byte comparison by 39.1% against the *fitted* scaled quaternary and even beats the **three-byte** quaternary on this slice. That does not establish better native execution: the polar warm table is 32 times larger than the scalar scale table, its addresses are less local, and table preparation is unmeasured. It is a real rate/distortion construction, not a claimed throughput win.

The ranking reverses under a sum-dominant consumer. The one-byte fitted scalar/scale grid beats polar by 9.9%, and the three-byte arbitrary FP16 scale cuts polar's response error by 75.4%. An obvious approach was to spend 6–8 bits on the important sum coordinate and consume that directly. It did not win here. The real held weights have heavy tails, so normal-quantile sum labels clip badly: the maximum held rotated coordinates reach 5.29 and 8.56 training standard deviations. Explicit tail labels improve 6+2 sum-dominant error from 1.25656e-5 to 4.98181e-6, still behind polar and scalar. More bits spent on one axis also means too few labels for the other unless its contribution is genuinely negligible. The direct-code structure survives, but its simple analytic quantizer loses this finite test.

The stored polar image for these 8,192 pairs would be 8,194 bytes including its two-byte gain, versus 24,576 bytes for the per-pair FP16 control. It needs a 1,024-byte warm table in the consumer and an offline index-selection pass over 256 fixed points per pair. The code reports storage separately from numerical error. It does **not** time the reader or claim that the fixed constants have no compiled-program cost. Each method's warm table size, gain bytes, fitted scale values, weight error, source SHA256, and individual axis errors are in [results.json](results.json).

## Bounded nonlinear consumer transfer

I also ran a small SiLU gate/up/down slice with actual layer-0 BF16 inputs captured from Qwen3-0.6B text. It uses gate/up output rows 8–11 and input columns 0–127, all 32 down-projection outputs 0–31 for those four hidden rows. Every other gate/up coordinate is **absent**, not held uncompressed in the background. The exact slice map is `y = W_down[0:32,8:12] (SiLU(W_gate[8:12,0:128] x) ⊙ (W_up[8:12,0:128] x))`. The consumer uses the same original BF16 down weights for all arms. This is a 512-pair nonlinear subnetwork, not the complete 3,072-channel MLP. Its restricted inputs cannot predict whole-model quality.

The RMS gain and fixed scalar grid are the same as above, calibrated on *different* weight rows 0–7. The fitted scalar scale table also uses only those weight rows. Each of the 512 held-row indices starts at Euclidean nearest code; two coordinate sweeps then choose among all 256 fixed indices using the exact **training** slice-output squared error for each candidate, with the other assigned indices held fixed. A fourth arm fits the 16 scalar FP16 scales to the training response after a preliminary index sweep, then repeats the two index sweeps. It has the same 32-byte metadata as the fitted scalar control. Neither FP16 scale fitting nor coordinate descent proves a global optimum. The separate validation text never chooses a code or table.

The original-producer and quantized-producer captures are paired, real model inputs. The latter has binary Q/K and norms with a narrow rank-28 V/O before the MLP; the teacher has the original producer. Each arm fits on 64 train positions `[320,384)` and is scored on 128 separate validation positions `[576,704)`. These validation windows were inspected in earlier work and are not fresh model acceptance. FP64 arithmetic replays the BF16 source weights and BF16 captured inputs, rather than claiming the GPU's BF16 output bits.

These numbers are after index sweeps. Polar also has lower held error before the sweeps; the receipt records both stages and weight errors. Its advantage over the best held scalar arm is 18.9% on the original producer and 26.7% on the quantized producer. The response-fitted table does not dominate the fixed scalar table: FP16 rounding followed by a short greedy reassignment can end in a worse local index basin, and the small training response does not reliably select the held winner. All four methods have **one index byte per pair**, not identical total storage. The 512 indices cost 512 bytes; polar and fixed scalar add a two-byte FP16 gain, while either learned scalar table adds 32 FP16 bytes. The 256 BF16 bytes of down weights are common to all. Polar also prepares a 1,024-byte table versus 32 bytes for either scalar reader. The polar result is a rate/response improvement on this slice, not a native-speed claim.
