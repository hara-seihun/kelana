# Lazy exact sampling from integer weights

A greedy winner certificate does not sample a distribution. Here is a finite stochastic counterpart that can stop reading a proposed token's weight after its high byte. It is exact, but its cost depends on the envelope, not just the entropy of the target distribution.

Run `python3 research/speculative-maps/lazy-sampling/experiment.py` from the Kelana root. The script writes [results.json](results.json), exhaustively checking every one of 1,472 possible proposal coordinates in each context. It uses only the Python standard library and no model or GPU.

## Contract and construction

Eight dynamically changing nonnegative integer weights `w_i` define `P(i)=w_i / Σw`, with `Σw>0`. A static, **certified** envelope `U=(1024,64,64,64,64,64,64,64)` satisfies `w_i≤U_i` in every admitted context. The bounds must be guaranteed by the weight producer; checking them by reading every dynamic weight online would destroy the claimed saving. The source stores each `w_i` in two bytes, big-endian. A once-prepared two-byte cumulative envelope table stores `C_i=Σ_{j≤i}U_j`.

Draw an independent exact uniform integer `r∈[0,ΣU)` on each attempt. Scan the table to locate the unique index `i` with `C_{i-1}≤r<C_i`, and set `v=r-C_{i-1}`. Read only the high byte of `w_i`. This gives the certified interval `[256h,256h+255]`. Accept if `v<256h`; reject if `v≥256h+256`; otherwise read its low byte and accept precisely when `v<w_i`. Repeat on rejection. The first accepted index is the output. There is no cap on attempts, approximation or biased timeout fallback.

Each `(i,v)` occupies one equally likely cell of the proposal space. Exactly `w_i` of token `i`'s `U_i` cells pass `v<w_i`. Thus a single attempt accepts token `i` with probability `w_i/ΣU`, total acceptance probability is `Σw/ΣU`, and the first accepted token has probability `w_i/Σw`. Independence makes termination almost sure. The program checks the accepted-cell count for *every* proposal coordinate, not a histogram. It also couples every accepted cell to a full-weight inverse CDF: `q=Σ_{j<i}w_j+v` is an accepted rank in `[0,Σw)`, and full CDF sampling at `q` returns the same `i`. Conditional on acceptance, `q` is uniform. This is a decision-by-decision coupling, not an assertion that using the same raw random integer in two different samplers gives the same output.

## Costs, including the table

The input producer's dynamic weight computation is common to both samplers and excluded; the dynamic **weight reads** are not. The baseline reads all eight two-byte weights, totals them, then draws one uniform CDF rank. It reads 16 dynamic bytes, performs eight additions and up to eight CDF comparisons per output. It does not need a prepared table. If it caches dynamic cumulative sums for subsequent draws from the *same* context, charge another 16 dynamic bytes written at first use. Here each case is one draw per fresh context.

Preparing the static envelope once reads 16 bound bytes, writes 16 cumulative bytes, makes eight additions and checks eight bounds. Each lazy attempt reads two metadata bytes per scanned cumulative endpoint, one or two dynamic source bytes, makes one endpoint comparison per scanned endpoint and one to three weight comparisons. It draws one independent uniform coordinate per attempt. The table preparation is amortized over contexts sharing the **same proven static envelope**, never given free for a one-shot context. For `N` outputs, add `32/N` preparation traffic bytes per output to the reported recurring reads. No dynamic weight lookup, prefix sum, bound check or proposal-table build has been given away online. The offline fixture assertion checks that these particular weights obey the envelope; an implementation must supply that invariant without a runtime full scan.

| Dynamic weights, first then other seven | Expected attempts | Dynamic bytes/output | Metadata bytes/output | All recurring read bytes/output | Full CDF reads |
| --- | ---: | ---: | ---: | ---: | ---: |
| `1000, 8×7` | 1.394 | 2.061 | 6.182 | 8.242 | 16 |
| `125, 1×7` | 11.152 | 16.485 | 49.455 | 65.939 | 16 |
| `128, 56×7` | 2.831 | 4.185 | 12.554 | 16.738 | 16 |
| `1000, 56×7` | 1.057 | 1.563 | 4.690 | 6.253 | 16 |

These are exact finite expectations rounded to three decimals. For any counted per-attempt quantity `c(r)`, the expected total until acceptance is `Σ_{r=0}^{ΣU-1} c(r) / Σw`. The concentrated-high case saves 7.758 recurring read bytes per sample, before static preparation; it needs at least five samples with this reusable envelope to repay the 32 preparation-traffic bytes on this metric. The spread case already exceeds the full-read baseline, and the low case is much worse. An entropy-only selector would make a bad decision: `1000,8×7` and `125,1×7` have **identical normalized laws and identical entropy** because one is exactly eight times the other, yet their expected traffic differs eightfold under the same static envelope. The acceptance rate and envelope fit are the useful difficulty signals here. They are not free either if estimating them requires reading the dynamic weights.

A uniform integer draw is counted as one random coordinate, not priced in bytes or cycles. Generating unbiased bounded integers with actual random bits has variable cost; rejection can require arbitrarily many proposals. Metadata accesses are logical two-byte table reads, not cache-line transactions. The Python code really indexes separate bytes for high and low weights, but these numbers are not timings, cache-miss counts or a SIMD/GPU implementation. Bounds are constants known before the context, while weights change per context. If the envelope is computed from the dynamic scores instead, its preparation must read those scores and build a new table; the 8.242-byte claim no longer applies. If an actual neural head must first compute/materialize every logit to know whether it satisfies the envelope, this toy saves no head production. Arbitrary floating softmax logits, rounded exponentials and continuation state are outside the contract.

The next useful experiment is a real score producer with cheap valid per-token integer-weight envelopes and a layout that fetches only the selected source bytes. Measure bounds construction, producer work, irregular head transactions and random generation alongside repeated acceptance, then compare complete target-sampling and continuation-state costs against a tuned full softmax. Without that producer-level proof, this remains a finite exact sampler, not a neural decoding speedup.
